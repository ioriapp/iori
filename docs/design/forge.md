# Forgeとの連携

GitHub・Forgejo・GiteaのCIとIssueをioriの中で読む画面、Hostの設定の「連携」、Issueから作業を始める操作、AIエージェント向けのForgeを読むコマンドを作る・変える時に読む。サイドバーのPR・CIの印は[Git View](git-view.md#画面の構成)、worktreeの作成画面は[worktreeとフォルダー](worktrees.md#worktreeを作る)、Forgeとの通信と認証情報の保管は[技術設計](../architecture.md#filesとgit)が持つ。

## 範囲

ioriはForgeの情報を読むことを基本にする。読むのは、CIの実行・job・ログと、Issueの一覧・本文・コメントである。書き込みは、AIエージェントがPull requestを作るコマンド（`iori pr create`）だけを持つ。通知、Pull requestの本文とレビューのコメント、Release、それ以外の書き込み（コメント、Issueを閉じる、CIのやり直し）は持たない。画面とコマンドでは、Forgeが定義する名前（Issue、CI、workflow、job、step、ラベル）をそのまま使う。

手元のGitとForgeは別に扱う。Forgeが未設定の時や、Forgeを読めない時も、Files・Git・Terminal・CLIは普段どおり使える。

## 対象のリポジトリ

CIの対象は、[PR・CIの印](git-view.md#画面の構成)と同じく、表示中のworktreeのブランチのpush先（`@{push}`）のリポジトリとブランチの、最新のcommitである。Issueの対象は、main worktreeで引数なしの `git push` が使うremote（Gitの規則で決まり、pushしていなくても決まる）のリポジトリとし、どのworktreeから開いても同じ一覧にする。Forgeの判定と開くURLは、印と同じく[ワークスペースの設定の「Git」](settings.md#ワークスペースのgit)のremoteとWebサイトに従う。

## 連携の設定

設定の「Host」の下の「連携」（英語の表示はIntegrations）で、そのHostがForgeを読むための認証を扱う。Forgeごとに設定の項目を増やさず、この1つの項目の中に節を並べる。GitLabなどを足す時も、この項目に節を足す。

### GitHub

そのHostの `gh` のログインの状態を表示する。ログインしているアカウントを並べ、有効なアカウント（`gh auth switch` で切り替えるもの）を示す。`gh` が無い時は「`gh` が見つかりません」、ログインしていない時は「このHostのTerminalで `gh auth login` を実行してください」と示す。ioriはここでログインやアカウントの切替をせず、tokenを表示しない。リポジトリごとに使うアカウントは[ワークスペースの「Git」](settings.md#ワークスペースのgit)の「GitHubのアカウント」に従う。

### Forgejo・Gitea

サイト（WebのURLのorigin）ごとにtokenを1つ登録する。一覧には、登録したサイトと、このHostで開いたワークスペースのremoteからForgejo・Giteaと分かったサイトを、ホスト名の順に並べる。各行にはサイトのURL、状態、操作を置く。

| 状態         | 示すこと                                              | 操作                      |
| ------------ | ----------------------------------------------------- | ------------------------- |
| 未登録       | 公開のリポジトリだけを読んでいること                  | 「tokenを登録」           |
| 登録済み     | tokenの持ち主のアカウント名（読めた時だけ）           | 「tokenを替える」「削除」 |
| 権限不足     | 足りない権限（例: `read:issue`）                      | 「tokenを替える」「削除」 |
| tokenが無効  | サイトがtokenを受け付けないこと（期限切れ・取り消し） | 「tokenを替える」「削除」 |
| つながらない | サイトにつながらないことと、最後に試した時刻          | 「再試行」「削除」        |

権限不足・tokenが無効・つながらないは、そのサイトを最後に読んだ結果（登録、画面、コマンド）で示し、次に読めた時に戻す。

一覧の下の「サイトを追加」で、サイトのURLとtokenを入れて「追加」する。行の「tokenを登録」「tokenを替える」は、その行の下にtokenの欄と「登録」を開く。どちらもEnterでも保存する。追加・登録の時はHostがサイトへ問い合わせ、Forgejo・Giteaとして応答しない、tokenを受け付けない、つながらない時は保存せず、欄のそばに理由を出して入力を残す。権限の不足は、実際に読めなかった時に状態へ出す。tokenの欄の説明に、必要な権限（`read:repository` と `read:issue`。アカウント名を示す時と[AutomationsのIssue](automations.md#issue)を使う時は `read:user` も、`iori pr create` を使う時は `write:repository` も）を書く。

tokenは入れた後に画面へ出さず、欄を空に戻す。保管は `gh` と同じく、HostのOSの資格情報の保管所を使い、無い時はHostのデータフォルダーの本人だけが読めるファイルに置く（[技術設計](../architecture.md#filesとgit)）。ファイルに置くHostと、URLがhttpのサイトでは、tokenの欄の下にそのこと（httpではtokenが暗号化されずに送られること）を1行で示す。tokenは画面・記録・会話・AIエージェントへ出さない。

「削除」は確認を1回出し、「このHostから〈サイト〉のtokenを削除します。非公開のリポジトリとIssueは読めなくなります。tokenそのものは、サイトで無効にするまで使えます。」と示す。

## CIの詳細

サイドバーのworktreeの行の[CIの印](git-view.md#画面の構成)を押すと、ブラウザーではなく、親のworktreeの配置の中に「CI」のタブを開く。既にあればそこへ移り、表示対象を押した行のworktreeへ替える。スマホではドロワーの同じ印から全画面で開く。

上端の行に、Gitのタブと同じworktreeの切替、対象のcommit（短いhashと件名）、読み直し、「ブラウザーで開く」を置く。「ブラウザーで開く」は、失敗している実行、無ければ実行中の実行、全て通過ならそのcommitのCIの画面を開く。十分な幅では左に一覧、右に選んだjobの詳細を並べ、狭い幅とスマホでは一覧と詳細を一画面ずつ出す（[Git View](git-view.md#画面の構成)と同じ）。一覧は名前・event・時間を1行に並べるので、初期の幅はGit Viewの4分の1より広い本体の38%（320px未満にはしない）とし、Issuesの一覧も同じにする。

- **一覧**: そのcommitのCIを実行（workflow）ごとにまとめ、その下にjobを並べる。各行に名前、状態（Failed・Running・PassedなどForgeの状態）、かかった時間を示す。幅が足りない時は、event名（`pull_request_target` など）や結果の説明を名前より先に縮め、入らなければ出さない。Forgejoはjobの時間を返さないので、Forgejoのjobには時間を出さない。状態の印はサイドバーの[CIの印](git-view.md#画面の構成)と同じアイコンと色にする。ioriの知らない状態の語は、その語のまま灰の印で示し、失敗・実行中・通過のどれにも数えない（サイドバーの印も同じ）。実行は失敗、実行中、通過の順に、同じ状態の中はworkflowの名前の順に並べ、jobはForgeが返す順にする。やり直した実行は最新の回を示す。jobを持たない結果（外部のサービスのcommit statusやcheck run）は、名前・状態・説明と「ブラウザーで開く」だけの行にする。
- **開いた時の選択**: 失敗したjob、無ければ実行中のjob、無ければ最初のjobを選ぶ。
- **jobの詳細**: job名、状態、かかった時間、そのjobをブラウザーで開くボタン、ログを示す。ログはjob全体を1本で示し、stepの一覧を返すForge（GitHub）では、ログの上にstepを並べて失敗したstepを示す。ログは開いた時に失敗したstepの終わり（分からない時はログの末尾）を見せ、上へスクロールすると前の行も読める。行頭の時刻は出さず、色の指定はTerminalと同じ色で示す。長い行はログの中で横に読め、スマホでは折返しを切り替えられる。終わっていないjobは、Forgeが返す所までのログを示す。GitHubはjobが終わるまでログを返さないので、stepの一覧と、ログの所に「GitHubは、jobが終わるまでログを返しません。」と「ブラウザーで開く」を示し、jobが終わった後の[読み直し](#読み直し)でログを示す。
- **ログを読めないForge**: 実行・job・ログを読む口を持たないForge（v16より前のForgejoなど）では、一覧をcommit statusから作り、詳細のログの所に「ブラウザーで開く」だけを置く。どの口を使えるかはForgeに問い合わせて決め、使えない操作は出さない。
- **CIが無い時**: 対象のcommitにCIが無い時は「このcommitのCIはありません。」とだけ示す。ブランチにpush先が無い時は「このブランチのpush先が見つかりません。pushすると、そのcommitのCIを表示します。」とだけ示す。

## Issues

サイドバーの各リポジトリの行に、worktreeを作る「＋」の左へ、Issuesを開くアイコンのボタン（名前は「Issues」）を置く。アイコンは `CircleDot`（[UIの定義](ui.md#画面の骨組み)の表）で、すぐ下のworktreeの行のCIの実行中の印とは別のアイコンにする（[Git View](git-view.md#画面の構成)）。対象のリポジトリのForgeが分かった時だけ出し、Gitでないフォルダーには出さない。開いているIssueの数は出さない（数のために定期的に読まない）。スマホのドロワーも同じ行に置く。

Issueはリポジトリのもので、Forgeを読むのもworktreeを作るのも、そのHostのcloneで行う。同じリポジトリを複数のHostにcloneしている時は、それぞれのHostのリポジトリの行から開き、そのHostの認証で読み、そこから始めたworktreeはそのHostに作る。

ボタンを押すと、本体が表示している配置がそのリポジトリのworktreeのものならその配置に、違えばそのリポジトリのmain worktreeを選んでその配置に、「Issues」のタブを開く。既にその配置にIssuesのタブがあればそこへ移る。焦点の移し方はサイドバーからFilesなどを開く時と同じにする（[タブと分割](workspace-layout.md#タブと分割)）。

十分な幅では左に一覧、右に選んだIssueの詳細を並べ、狭い幅とスマホでは一覧と詳細を一画面ずつ出す。詳細から戻ると、同じ一覧・絞り込み・選択・スクロール位置へ戻る。

- **一覧**: 上端に、リポジトリ（`owner/repo`）とForgeの種類、状態の切替（Open・Closed）、ラベルの絞り込み、読み直し、「ブラウザーで開く」を置く。既定はOpen。ラベルはそのリポジトリのラベルから複数選べ、選んだラベルを全て持つIssueに絞る（GitHub・Forgejoの絞り込みと同じ）。各行に状態の印（OpenはPRの印のOpenと同じ緑、Closedは灰）、題名、番号、ラベル（Forgeのラベルの色の小さな丸と名前）、作成者、最後の更新からの時間、コメントの数を示す。作成の新しい順に並べ、Pull requestは含めない。スクロールに合わせて続きを読み、「さらに読み込む」は置かない。
- **詳細**: 上端に3行を置く。1行目は題名と番号で、幅いっぱいに折り返して示す。2行目は状態、作成者と作成日時。3行目は「このIssueで始める」と「ブラウザーで開く」を左寄せで並べる。どの幅でも同じ並びにする。その下にラベルと担当者、本文、コメントを古い順に並べる。本文とコメントは[FilesのMarkdown](files-view.md#markdown)と同じ決まりで描画する。画像は、画像の説明の文字のリンクとして示し、押すとブラウザーで開く。リポジトリは読めるのにIssueが消された・移された時は「このIssueは見つかりません。」とだけ示す。
- **空**: 該当するIssueが無い時は「Open のIssueはありません。」のように示し、ラベルで絞っている時は「絞り込みを解除」を置く。リポジトリがIssueを使っていない時は「このリポジトリではIssueを使っていません。」とだけ示す。

## Issueから始める

Issueの詳細の「このIssueで始める」は、そのリポジトリの[worktreeを作る](worktrees.md#worktreeを作る)画面（PCはダイアログ、スマホは全画面）を、次の値を入れた状態で開く。ユーザーは値を直してから「作成」または「この場所で（worktreeを作成しない）」で始める。自動では始めない。

- **名前**: 題名がASCIIの文字（英数字・空白・記号）だけの時は、[`delegate --worktree new` の名前](worktrees.md#作成後に実行するコマンド)と同じく題名をASCIIの英数字とハイフンへ整え（英数字以外の並びをハイフン1つにし、小文字にして前後のハイフンを除く）、24文字以内で単語の途中で切らない所までにして（24文字以内に単語の切れ目が無い時は24文字で切る）、`〈番号〉-〈整えた題名〉` にする（例 「Keep the scroll position after reconnecting」は `134-keep-the-scroll-position`、「Keep the token out of the logs」は `2-keep-the-token-out-of`）。それ以外の文字（日本語など）を含む時と、整えた題名が空になる時は `issue-〈番号〉`（例 `issue-142`）。
- **最初の指示**: 「Issue #123 を進めてください。本文とコメントは `iori issue show 123` で読めます。」（英語の表示では英語の文）。
- **ベースブランチ、CLI・Team、作成後に実行するコマンド**: ふだんの既定値のまま。

始めたCLIは、`iori` のコマンドで最新の本文とコメントを読む。ioriはIssueの本文を指示へ埋め込まず、tokenをCLIへ渡さない。

## AIエージェント向けのコマンド

ioriが起動する全てのCLI（チームの親・子、チームでない会話、Automationの会話）で、Forgeを読む `iori` のコマンドを使える。ユーザー自身のCLIの設定が書き込みを許さないsandbox（Codexのread-onlyなど）の会話では、実行にCLIの承認が要る（[子の起動と作業場所](linked-agents.md#子の起動と作業場所)）。チームのコマンド（`iori delegate` など）はチームの会話だけで使える。呼び方、`--json`、`--help` は[Linked Agentのコマンド](linked-agents.md#親と子のコマンド)と同じ決まりにする。

```sh
iori issue list [--state open|closed|all] [--label NAME]... [--limit N]
iori issue show N
iori ci list
iori ci log [JOB_ID]
iori pr create --title TITLE [--body TEXT | --body - | --file PATH] [--issue N]
```

| コマンド          | 返すもの                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `iori issue list` | Issueの番号・状態・題名・ラベル・更新日時。既定はOpenの30件（`gh issue list` と同じ）で、`--limit` で件数を変える。続きがある時は最後にそのことを1行で示す。`--label` は複数付けられ、全てを持つIssueに絞る                                                                                                                                                                                                                                                                                                                                                                  |
| `iori issue show` | Issueの題名・状態・作成者・ラベル・本文と、全てのコメント（作成者・日時・本文）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `iori ci list`    | 呼んだCLIのworktreeのブランチのpush先の最新のcommitのCI（実行、job、状態、jobのID）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `iori ci log`     | 指定したjobのログ。jobのIDを省くと、`iori ci list` と同じcommitの失敗したjobのログ                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `iori pr create`  | 呼んだCLIのworktreeの今のブランチを、Hostが自分の認証でpush先へpushし（force-pushはしない）、そのリポジトリの既定のブランチへのdraftのPull request（Forgejo・Giteaは題名の先頭に `WIP:`）を作って、そのURLを返す。本文の渡し方（`--body -` は標準入力、`--file` は作業フォルダーの中のファイル）は `iori delegate` と同じ。`--issue N` を付けると本文の末尾に `Closes #N` を足す。同じブランチのPull requestが既にあれば、作らずにそのURLを返す。既定のブランチからは作らない。Forgejo・Giteaのtokenに書き込みの権限（`write:repository`）が無い時は「権限が足りない」を返す |

対象のリポジトリとブランチは、呼んだCLIのworktreeから[画面と同じ規則](#対象のリポジトリ)で決める。毎回Forgeから読み（そのサイトがどのForgeかの判定も、画面の読み直しと同じくやり直す）、本文とログはForgeが返すまま出す。読めない時は[画面と同じ理由](#失敗の示し方)と回復の操作（例: 設定の「連携」でtokenを登録する）を英語の短い文で返す。認証はHostが持ち、tokenをCLIの環境・引数・答えに出さない。

## 読み直し

CIとIssuesの画面は、開いた時（隠れていたタブを再び表示した時を含む）と、ユーザーの読み直しで読む。Issueの詳細は選んだ時に読む。CIの画面は、サイドバーのCIの印が変わった時（pushや状態の変化）にも読み直す。読めない理由を示しているCI・Issuesの画面は、[連携](#連携の設定)でtokenを登録・替える・削除した時にも読み直す。CIの画面の読み直しと再試行では、そのサイトがどのForgeかの判定もやり直す。読み直しの間と、読み直しに失敗した時は、最後に読めた内容を保つ。サイドバーの印の読み直しは[Git View](git-view.md#画面の構成)に従う。

## 失敗の示し方

Forgeを読めない時は、理由を区別して、その対象（CI・Issuesの画面、連携の行、コマンドの答え）のそば一か所に、起きたことと回復の操作を示す（[表示と失敗の案内](../product.md#表示と失敗の案内)）。

| 理由           | 示すこと                                                                                                           | 回復の操作                                          |
| -------------- | ------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------- |
| tokenが無い    | 〈サイト〉のtokenが登録されていないこと。GitHubは `gh` にログインしていないこと（`gh` が無い時は見つからないこと） | 「連携を開く」。GitHubは `gh auth login` の案内     |
| tokenが無効    | 〈サイト〉がtokenを受け付けないこと                                                                                | 「連携を開く」                                      |
| 権限が足りない | tokenに足りない権限。GitHubは読めるアカウントが無いこと                                                            | 「連携を開く」                                      |
| 見つからない   | リポジトリ（`owner/repo`）が見つからないこと                                                                       | 「ワークスペースの設定を開く」（remoteとWebサイト） |
| つながらない   | 〈サイト〉につながらないこと                                                                                       | 「再試行」                                          |
| 回数の上限     | APIの回数の上限に達したことと、読めるようになる時刻                                                                | 「再試行」                                          |

GitHubは、アカウントが読めない非公開のリポジトリにも「見つからない」と答える。そのため、HostのどのGitHubのアカウントでも読めない時は「権限が足りない」として示す。アカウントを順に試すのはリポジトリを読めるかを決める時だけで、読めるアカウントで中の1件（Issue、jobのログ）が見つからない時は、リポジトリの理由を出さずにその物が無いとして示す（始まる前に終わったGitHubのjobは「このjobは実行されませんでした。」）。

## スマホ

CIはドロワーのworktreeの行のCIの印から、jobの一覧を失敗したjobを選んだ状態で全画面に開く。Issuesはドロワーのリポジトリの行のボタンから全画面で開く。一覧と詳細は一画面ずつ行き来し、Androidの戻る操作は詳細から一覧へ戻る。「このIssueで始める」は全画面のworktreeの作成画面を開く。設定の「連携」は、ほかの設定の項目と同じく一覧から全画面で開く。
