# CLIの定義ファイル

読むのは、iori が正式に対応していない CLI を、ユーザーや他の人が足せるようにする仕組みを変える時である。正式に対応した CLI の個別の振る舞いは、各 CLI の設計（[Pi](pi.md) など）と[技術設計](../architecture.md#cli)が持つ。

## 目的

iori は、世界中の AI コーディング CLI を使えるようにしたい。ただし、Orca のように CLI ごとにコードを足し続けると、iori の保守がその数に比例して重くなる。そこで、CLI ごとの違いを **値で書いた定義（定義ファイル）** に寄せる。ユーザーや他の人が、定義ファイルを足すだけで CLI を足せるようにする。

ほとんどの CLI は、モデルの指定・最初の指示・再開を起動引数で持つ。hooks を持つ CLI の多くは「外部コマンドを呼び、stdin へ JSON を渡す」形で、違いは設定ファイルの場所・書式・出来事の名前・項目の名前に収まる。

## 3つの層

| 層               | 中身                                                                       | 誰が足せるか           | 動く場所                               |
| ---------------- | -------------------------------------------------------------------------- | ---------------------- | -------------------------------------- |
| 定義ファイル     | 検出・起動・モデル・チーム・再開・hooks の対応を値で書いた JSON            | iori、ユーザー、他の人 | Host が読み込むだけ                    |
| 付属のファイル   | CLI へ置く橋渡しの部品と、トークン量・利用枠を読み込むスクリプト、アイコン | iori、ユーザー、他の人 | CLI の中、または Host とは別のプロセス |
| 正式対応のコード | 定義ファイルで表せない CLI 固有の処理                                      | iori だけ              | Host                                   |

- Host は、他の人が書いたコードを自分のプロセスへ読み込まない。付属のファイルは、CLI が読み込むか、Host が別のプロセスとして起動する。
- 正式対応の CLI も、定義ファイルで表せる部分は定義ファイルで書く。コードに残す処理は、下の「正式対応との関係」に挙げる。

## 置き場所と追加

- **iori が同梱する定義**: リポジトリの各 CLI のフォルダー（`apps/host/src/cli/<id>/definition.json`）に置き、Host と一緒に配る。正式対応の CLI のコードも同じフォルダーに置く。iori が実物で確かめた CLI に加え、公式の資料で引数と hooks を確かめた CLI も同梱する。画面では両者を区別せず、どちらで確かめたかはユーザー向けの文書（README）に書く。
  - 資料だけで確かめた定義が誤っていた時、起動の引数の誤りは CLI 自身がエラーで知らせる。hooks の誤りは、CLI が iori の hook を呼ばないだけなので、応答の状態が出ないことでしか分からない。そのため、チームの子への最初の指示は、hooks の出来事を待たずに渡す（下の `launch.initialPrompt`）。
  - トークン量・利用枠のスクリプトは、間違っていても画面からは気づけない。スクリプトだけは、本物の CLI の出力で確かめたものを同梱する。
- **ユーザーが足す定義**: Host の保存先の `cli-definitions/<id>/` に、`definition.json` と付属のファイルを置く。Host はこのフォルダーを読み込む。
- **`id`**: 英小文字・数字・`-` だけにする。フォルダー名と `definition.json` の `id` が違う定義は読み込まない。
- **同梱の定義の上書き**: ユーザーの定義が同梱の定義と同じ `id` を持つ時は、ユーザーの定義を使う。CLI の変更に iori の更新が追いつく前に、ユーザーが自分で直せるようにするためである。
  - 上書きしても、正式対応のコードに残る処理（利用枠・トークン量など）はそのまま使う。上書きされるのは定義ファイルの部分だけである。
  - 上書き中の CLI の行には「ユーザー定義」と表示し、「同梱の定義に戻す」で上書きを削除できる。上書きが残ったままだと、iori の更新で直った同梱の定義が使われないためである。
- **置き場所**: 定義の追加・編集・削除は、AIエージェントの画面の、Host ごとの CLI の一覧で行う（[AI Agents/Teams](agents-and-teams.md)）。定義は Host ごとに持つので、Client の設定の画面には置かない。
- **保存の時**: Host でその CLI が見つからなくても保存する。CLI を入れる前に定義を足す使い方を止めないためである。
- 共有は、ユーザーがファイルを受け渡して行う。iori はネット上から定義を自動で取りに行かない。

## 画面

画面の文言は下の表のとおりにし、説明の文を足さない。

### 一覧

- **並び**: 正式対応 → 同梱の定義 → ユーザーの定義（足した順）→ 読み込みに失敗した定義。
- **ユーザーの定義の表示**: ユーザーの定義と、同梱の定義を上書きした定義の行には、名前の横に小さく「ユーザー定義」と表示する。
- **見つからない CLI**: Host で見つからないユーザーの定義と、同梱の定義を上書きした定義の行には「このHostで見つかりません」と表示する。上書きした定義は、見つからなくても「同梱の定義に戻す」で戻せるようにするためである。上書きしていない同梱の定義の CLI で見つからないものは出さない。
- **読み込みに失敗した定義**: 形の合わない定義は、フォルダー名を名前にした行に、「定義を読み込めませんでした」と理由の2行を表示し、「定義を編集」「削除」を置く。開く詳細は持たない。
- **機能ごとの状態**: 一覧の行には出さない。
- **アイコン**: 定義の `icon` の画像を出す。`icon` の無い定義は、共通の CLI のアイコンにする。同梱の定義のアイコンは、どの CLI かを示す表示として、正式対応の CLI と同じく公式の素材（CLI 専用のロゴが無ければ提供元の会社のマーク）を Client に同梱し、出典を `apps/client/third-party/cli-icons/README.md` に書く。公式の条件が製品の中での利用を断っている CLI（Kimi Code）には同梱せず、共通のアイコンのままにする（ユーザーが下の「アイコン」の行で付けられる）。

### 行を開いた詳細

今の詳細（利用枠、同時実行の上限、起動時の引数）の後に、次の2つの節を置く。起動コマンドを `shell` の形で書いた定義（名前とコマンドから作った定義など）には「起動時の引数」を出さない。引数は起動コマンドの行そのものを直して変える。

- **「対応状況」の節**: 機能を列名にした横向きの2行の表（1行目が機能、2行目が値）。狭い画面では3列ずつ2段に折り返し、横にスクロールさせない。
  - 機能: 応答の状態、Attention、会話の再開、チームの子、トークン量、利用枠。
  - 値: 「利用可能」以外は弱い前景色で表示する。

    | 値       | 条件                                                                                               |
    | -------- | -------------------------------------------------------------------------------------------------- |
    | 利用可能 | 定義ファイルかコードがその機能を持つ                                                               |
    | 利用不可 | 定義ファイルでその機能を `"unavailable": true` としている、またはその CLI のバージョンでは使えない |
    | 未定義   | 定義ファイルもコードもその機能を持たない                                                           |

  - 「未定義」がある時だけ、表の下に「使えるようにする方法」（ユーザー向けの文書へのリンク）を置く。
  - 同梱の定義には、調査で手段が無いと分かった機能（hooks の無い CLI の応答の状態など）を `"unavailable": true` で書き、「利用不可」と「未定義」をユーザーが見分けられるようにする。
  - `plugin-file` の定義では、応答の状態は常に、`sends` に書いた機能（`attention`・`tokens`）をその定義が持つものとして扱う。
- **「アイコン」の行**: 今のアイコンと「画像を選ぶ」、ユーザーが付けたアイコンがある時は「共通のアイコンに戻す」（同梱の定義を上書きした定義では「同梱のアイコンに戻す」）。選べるのは SVG と PNG。選んだ画像は定義のフォルダーへ置き、ライトとダークの両方に使う（定義の `icon` の `light` に書き、`dark` を削除する）。ダークのテーマで別の画像を使う時は、定義の JSON の `icon.dark` に書く。確認は出さない。名前とコマンドから作った定義にも置く。
- **「定義」の節**: 「定義を編集」と、ユーザーの定義なら「削除」、同梱を上書きした定義なら「同梱の定義に戻す」。説明の文は置かない。

### CLIを追加

一覧の下の「CLIを追加」の節の中で開く。「追加方法」で次の3つから選ぶ。

| 追加方法               | 欄                                                                                                                                                            | 確認       |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------- |
| 名前とコマンド         | 名前、起動コマンド、モデルの引数（Host が `--help` から見つけた時は「`<コマンド> --help` から自動入力」）、モデルの候補（「コマンドで取得」か「手動で入力」） | 出さない   |
| JSON                   | 定義の JSON（欄の中に薄い例）                                                                                                                                 | 追加の前に |
| ファイルをアップロード | 「ファイルをアップロード」のボタン（複数のファイルを選べる）と、選んだファイル名                                                                              | 追加の前に |

- 名前とコマンドから作った定義は、Host が最小の定義（`id`・`name`・`command` とモデルの項目）として保存する。`id` は名前から作る（英小文字・数字・`-`。それが残らない名前は、名前から作った `cli-` で始まる値）。起動コマンドは `"command": { "shell": "<起動コマンド>" }`、モデルの引数は空白で分けた `launch.model`、モデルの候補は `"models": { "list": { "shell": "<コマンド>", "format": "lines" } }` か `"models": { "candidates": [...] }` で書く。`shell` の形は、名前とコマンドの欄と同じく シェル の規則で扱う。
- 「ファイルをアップロード」では、定義の JSON と、その中で名前を書いたファイル（アイコン・部品・スクリプト）を選ぶ。ファイルは何回かに分けて選べ、選んだファイルは一覧に足していく（選び直しで前のファイルを削除しない）。一覧の各ファイルに削除の操作（×）を置く。同じ名前のファイルを選んだ時は、後に選んだものに替える。選んだ中の JSON のファイルが1つならそれを定義として読み、複数ある時は `definition.json` という名前のものを読み込む。どちらでも決まらない時は「定義のJSONを1つ選んでください。」と表示する。Host は選んだファイルを定義のフォルダーへ置く。定義が名前を書いたファイルが選ばれていない時は、定義の JSON を選んだ時点から一覧の下に「次のファイルも選んでください: <ファイル名>」と表示し、揃うまで確認へ進まない（定義のフォルダーに既にあるファイルと、同梱の定義の上書きで同梱からコピーするファイルは選ばなくてよい。JSON の欄での追加・定義の編集も同じ。下の「ファイルを使う定義を JSON の欄で足す時」）。同梱の定義を上書きする時は、選ばれていないファイルを同梱の定義からコピーする（今の付属のファイルと同じ）。
- 入力の誤りは、操作の横に「名前とコマンドを入力してください。」「JSONを入力してください。」「ファイルをアップロードしてください。」、JSON の形の誤りは欄の下に理由（例「JSONの形式が正しくありません。」「launch.modelは文字列の配列にしてください。」）を表示し、確認へ進まない。

### 定義を編集

詳細の「定義」の行が、その場で欄に替わる。

- 名前とコマンドから作った定義は、追加と同じ欄で直す。確認は出さない。
- それ以外は「定義のJSON」の欄で直す。同梱の定義でも開け、保存すると上書きになる。中身を変えた保存では、下の確認を出す。同梱の定義では「上書き」の確認、ユーザーの定義と上書き済みの定義では「保存」の確認である。
- ボタンは「キャンセル」「保存」。

### 確認

| 場面                   | 題                                    | 本文                                                                                                             | ボタン                             |
| ---------------------- | ------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| JSON・ファイルで追加   | 「〈名前〉 の定義を追加しますか？」   | 「この定義を使うと、Host上で次の操作が行われます。」と、下の該当する項目だけ                                     | 「キャンセル」「追加」             |
| 同じ id の定義を上書き | 「〈名前〉 の定義を上書きしますか？」 | 同上                                                                                                             | 「キャンセル」「上書き」           |
| 中身を変えた保存       | 「〈名前〉 の定義を保存しますか？」   | 同上                                                                                                             | 「キャンセル」「保存」             |
| 削除                   | 「〈名前〉 の定義を削除しますか？」   | 「CLIの設定ファイルからioriが追加した項目も削除します。CLI本体の設定や会話、実行中のTerminalには影響しません。」 | 「キャンセル」「削除」             |
| 同梱の定義に戻す       | 「同梱の定義に戻しますか？」          | 「ユーザー定義は削除されます。」                                                                                 | 「キャンセル」「同梱の定義に戻す」 |

- 追加・上書き・保存の確認は、定義が次のどれかをする時だけ出し、該当する項目だけを表示する。どれもしない定義（CLI のコマンドを起動するだけの定義）とアイコンだけの変更は、確認なしで追加・保存する（名前とコマンドからの追加と同じ）。
  - 「実行するコマンド」: CLI 本体の起動ではないもの。`shell` の形で書いた起動コマンド・モデルの一覧のコマンド、トークン量・利用枠のスクリプトとコマンド
  - 「変更する設定ファイル」: hooks を書き込む CLI の設定ファイル
  - 「CLIのプラグイン」: CLI に読み込ませるプラグインのファイル（CLI のフォルダーへ置く `to` と、起動の引数で読ませる `args`）の置き場所
- 起動のコマンド（`claude` など）・バージョンの引数・CLI 本体へ渡すモデルの一覧の引数・アイコンは、足そうとしている CLI そのものの動きなので表示しない。他の人の定義が CLI の外で動かすもの・CLI に読み込ませるものだけを、埋もれないように表示する。
- **同じ id の定義の上書き**: 追加しようとした定義の `id` が、同梱の定義かユーザーの定義と同じ時は、追加でなくその定義の上書きとして扱う（配られた定義の新しいバージョンを入れ直す時に、削除してから追加する手間をかけない）。名前とコマンドからの追加でも、名前から作った `id` が同じなら同じく上書きになる。上書きでは、定義の項目が確認の対象を持たなくても、題「〈名前〉 の定義を上書きしますか？」の確認を出す（前の定義が置き換わるため）。対象の項目が無い時は本文を出さず、題とボタンだけにする。上書きでは、新しい定義が名前を書いているファイルのうち、選ばなかったものは前の定義のフォルダーのものを引き継ぎ（同梱の定義の上書きでは同梱からコピーする）、選んだものはそれに替える。新しい定義が名前を書いていない前のファイルは削除する。CLI の設定に書いた hooks は「書き込んだ物の片付け」と同じく、置き場所が変われば前の分を削除する。
- **ファイルを使う定義を JSON の欄で足す時**（定義の編集も同じ）: 定義がスクリプト・プラグイン・アイコンのファイルの名前を書いていて、そのファイルが選ばれていない時は、欄の下に「次のファイルも選んでください: <ファイル名>」と「ファイルを選ぶ」を出し、選んだファイルを「ファイルをアップロード」と同じ一覧に足す（削除の操作付き）。揃うまで確認へ進まない。同梱の定義の上書きでは、選ばれていないファイルを同梱からコピーするので知らせない。

## 定義ファイルの項目

```json
{
  "schema": 1,
  "id": "example",
  "name": "Example CLI",
  "command": "example",
  "aliases": ["example-cli"],
  "version": { "args": ["--version"] },
  "models": {
    "list": { "args": ["--list-models"], "format": "lines" }
  },
  "launch": {
    "model": ["--model", "{model}"],
    "permissions": { "yolo": ["--yolo"] },
    "initialPrompt": { "mode": "argument", "args": ["-i", "{prompt}"] },
    "directories": ["--add-dir", "{directory}"],
    "managedArguments": [
      { "names": ["--model", "-m"] },
      { "names": ["--yolo"], "arity": "none" }
    ]
  },
  "resume": { "args": ["--resume", "{sessionId}"] },
  "hooks": { "...": "下の「hooks」" },
  "tokens": { "script": "tokens.mjs" },
  "usage": { "script": "usage.mjs" }
}
```

| 項目                      | 内容                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `schema`                  | 定義の形のバージョン。知らないバージョンでも、読み込める項目だけを使う                                                                                                                                                                                                                                                                                            |
| `command`・`aliases`      | 検出に使うコマンド名。本人のログインシェルの PATH で探す。`command` は `{ "shell": "<コマンドの行>" }` とも書け、その行をそのまま起動に使い、行の先頭のコマンドをログインシェルが見つけられるかで検出する                                                                                                                                                         |
| `icon`                    | アイコンの画像（`{ "light": "icon.svg", "dark": "icon-dark.svg" }`）。値は定義のフォルダーの中のファイル名で、SVG か PNG。`dark` は省略できる。ファイルが無い・読み込めない時は、定義は読み、そのアイコンは共通のアイコンで出す（フォルダーの外を指す値と、SVG・PNG でない名前は形の誤り）。画像は `<img>` として描き、SVG の中のスクリプトや外の参照は動かさない |
| `version`                 | バージョンを出す引数                                                                                                                                                                                                                                                                                                                                              |
| `models`                  | モデル一覧を出す引数と出力の形（`list`）。`lines` は1行1つ、`json` は一覧の場所（`items`、例 `$.models[*]`）と各項目の `name`・`label`・`efforts` の項目名を書く。`list` は引数（`args`）の代わりに `shell` でコマンドの行を書ける。一覧を出せない CLI は固定の候補（`candidates`）を書く                                                                         |
| `launch.model`・`effort`  | チームの役割から付けるモデル・Effort の引数                                                                                                                                                                                                                                                                                                                       |
| `launch.permissions`      | 許可の選択肢。名前は CLI 自身のモードの名前（例: `yolo`、`plan`）にし、値はその時に付ける引数                                                                                                                                                                                                                                                                     |
| `launch.initialPrompt`    | 最初の指示の渡し方。`argument`（TUI を開いたまま引数で渡す）か `paste`（起動後に貼る）。`paste` は、その CLI が入力欄で bracketed paste を有効にすると確かめた時だけ書く。書いていない定義は、名前とコマンドから作った定義と同じく、入力欄が bracketed paste を有効にした時に最初の指示を貼る                                                                     |
| `launch.instructionFile`  | 指示のファイルを渡す引数（例: `["--append-system-prompt-file", "{instructionFile}"]`）。無い CLI では、最初の指示として「`{instructionFile}` を読んで従う」の一文を渡し、チームの子では続けて依頼のファイルを開く文を同じ1行に並べる（#335。コードで指示を渡す CLI（Codex）は除く）                                                                               |
| `launch.directories`      | チームのフォルダーを CLI に許す引数（`{directory}`）。ioriのコマンドの通信フォルダーと配送用のコピーのフォルダーが別の時（Linux）は、それぞれについて繰り返して付ける。無い CLI では、CLI 自身の許可に任せる                                                                                                                                                      |
| `launch.managedArguments` | ユーザーの起動引数から削除する、役割の項目と重なる引数（`names`、値を取らない `arity: "none"`・続く値を全て取る `"many"`、`-c` の設定の `keys`（末尾の `.*` はその名前で始まる全ての設定）、同じ意味の別の引数 `alsoRemove`） チームでない起動では `arity: "many"` の引数は削除しない（役割が決める値が無いため）。                                               |
| `resume`                  | 会話の再開の引数。会話 ID は hooks か受け口から受け取る                                                                                                                                                                                                                                                                                                           |
| 各機能の `unavailable`    | その CLI に手段が無いことを表示する（`"usage": { "unavailable": true }` など）。画面の「対応状況」に使う                                                                                                                                                                                                                                                          |

- **値の埋め方**: `{model}`・`{effort}`・`{prompt}`・`{sessionId}`・`{instructionFile}`・`{directory}` は、iori が起動のたびに埋める。値の無い項目（モデルを指定しない役割の `launch.model` など）の引数は付けない。
- **引数の順**: チームの起動の引数は、`launch` に書いた項目の順に付ける。正式対応の CLI で、コードの引数と混ぜる CLI（Claude Code・Codex・Pi）は、コードが順を決める。
- **許可の候補**: `launch.permissions` の名前を、チームの役割で選べる許可の候補にする。
- **シェル に解釈させない**: 定義ファイルの引数は、固定の部分も埋めた値も、1語ずつ引用して CLI へ渡す。`$(...)` などの シェル の展開を動かさない。ユーザーが自分で書く「起動時の引数」と、`shell` の形で書いた起動コマンド・モデルの一覧のコマンド（`"command": { "shell": "…" }`・`"models": { "list": { "shell": "…" } }`）だけは、シェル の規則で扱う。`shell` の形はどの定義にも書け、名前とコマンドから作った定義はこの形で保存する。確認の「実行するコマンド」には、その行をそのまま表示する。
- **パス**: 定義ファイルのパスは `~`・絶対パスと、環境変数による上書き（例: `{ "env": "CLAUDE_CONFIG_DIR", "default": "~/.claude", "path": "settings.json" }`。`path` はそのフォルダーの中のパス）で書ける。Windows でも同じ書き方で、Host が OS のパスへ直す。

## hooks

hooks を持つ CLI は、CLI の設定へ iori の hook のコマンドを書き込み、出来事を iori の状態へ対応付ける。

```json
"hooks": {
  "format": "claude-settings",
  "file": "~/.example/settings.json",
  "sessionId": "session_id",
  "transcript": "transcript_path",
  "toolId": "tool_use_id",
  "rules": [
    { "event": "SessionStart", "when": { "source": "compact" }, "ignore": true },
    { "event": "PostCompact", "ignore": true },
    { "event": "SessionStart", "state": "idle" },
    { "event": "UserPromptSubmit", "state": "active" },
    { "event": "PreToolUse", "state": "active", "tool": "tool_name" },
    { "event": "PostToolUse", "toolFinished": true },
    { "event": "PermissionRequest", "state": "waiting", "attention": "approval" },
    { "event": "Notification", "when": { "notification_type": "permission_prompt" }, "state": "waiting", "attention": "approval" },
    { "event": "Stop", "when": { "stop_hook_active": true }, "ignore": true },
    { "event": "Stop", "state": "done", "response": "last_assistant_message" },
    { "event": "StopFailure", "state": "done", "outcome": "failure", "failure": ["error_details", "error"] },
    { "event": "SessionEnd", "state": "stopped" }
  ]
}
```

- **書き込む先（`file`）**: ユーザー全体の設定のパス。書式は拡張子（`.json`・`.toml`・`.yaml`/`.yml`）で決める。プロジェクトの設定（`.vibe/hooks.toml` など）には書かない。リポジトリに iori の項目を入れないためである。ほかの拡張子の `file` と、`{command}` の無い `entry` は、知らない `format` と同じく、この Host が書かない hooks として扱う（その CLI の応答の状態は出ない）。
- **iori 専用のファイル（`own: true`）**: hooks 用のフォルダーに複数のファイルを置ける CLI（Kiro・Grok）では、`iori.json` などの iori だけのファイルを置く。ユーザーの設定ファイルには触れず、片付けはそのファイルを削除する（iori が置いたのではないファイルは下の「上書きしない」のとおり）。ファイル全体の形は `base`（例: Kiro の `{ "version": "v1" }`）に書く。確認では「変更する設定ファイル」に出す。
- **専用ファイルへの参照（`link`）**: `own: true` の時だけ、別の JSON 設定ファイルを `link.file` に指定できる。無ければ `link.base`（省略時は空）で作り、`link.set` の最上位の鍵と JSON 値を足す。値の中の `{file}` は専用ファイルの OS の絶対パスで埋める。既存の値がどれか1つでも異なる時は設定を変えず、専用ファイルも置かない。同じ値は保ち、無い鍵だけを足す。確認の「変更する設定ファイル」には参照元も出す。
- **形（`format`）**: iori の hook の項目を、ファイルのどこにどんな形で足すか。iori が書き込む処理を持ち、定義ファイルはどれかを選んで項目の名前を書く。
  - `events`: 出来事の名前を鍵にした表（`<at>.<出来事>` の配列）に、`entry` の形の項目を足す（Claude Code・Grok・VT Code・Hermes の形）。
  - `list`: 1つの配列（`<at>`）に、出来事の名前を項目に持つ `entry` の形の項目を足す（Kimi Code・Mistral Vibe・Kiro の形）。
  - `claude-settings`: `events` で `at` が `hooks`、`entry` が `{ "hooks": [{ "type": "command", "command": "{command}" }] }` のもの（Claude Code・Qoder・CodeBuddy・Grok）。道具の出来事（名前に `ToolUse` を含むものと `PermissionRequest`）の項目には `"matcher": "*"` を付ける。
  - `plugin-file`: 下の「プラグインだけを持つ CLI」
  - `at` は点で区切った場所（例: VT Code の `hooks.lifecycle`）。空の部分は書けない。`entry` の中の `{event}`・`{command}` を、iori が出来事の名前と iori の hook のコマンドで埋める。

  ```json
  "hooks": {
    "file": "~/.kimi-code/config.toml",
    "format": "list",
    "at": "hooks",
    "entry": { "event": "{event}", "command": "{command}" },
    "rules": [{ "event": "Stop", "state": "done" }]
  }
  ```

- **書き換え方**: 書式を保つ方法で、iori の項目だけを追加・削除する。ユーザーのコメント・並び・他の項目は変えず、ファイルの中で変わるのは iori の項目の部分だけにする。マーカーを付けた区画を文字として足す方法は採らない（ユーザーが `[hooks.lifecycle]` や `hooks:` を既に書いていると、同じ鍵が二重になる）。
  - YAML: `yaml` で解析して置き場所の位置を求め、iori の項目の行だけを元の文字列へ差し込む・切り取る。字下げはその場所の行に合わせる。流れの形（`{ }`・`[ ]`）の中には足さず、そこにある iori の項目も削除せずに失敗にする（同じ行のユーザーの項目を壊さないため）。`yaml` の Document を文字列に戻す方法は、ユーザーのコメントの字下げや空白まで変えるので採らない。
  - TOML: `@decimalturn/toml-patch` で書き換える。配列の表（`[[hooks]]`）の iori の項目を削除する時は、解析した位置で、その要素の区画と要素の中の区画を、それぞれ見出しの行から最後の鍵の行まで切り取る。要素の中の区画は、配列の次の要素までにある、鍵が配列の鍵で始まる区画である（TOML の決まり。例: `[[hooks]]` の後の `[hooks.x]`、VT Code の `[[hooks.lifecycle.stop]]` の後の `[[hooks.lifecycle.stop.hooks]]`）。最後の鍵の後のコメント・空行と、ほかの区画は残す（`toml-patch` は最後の鍵の後のコメントを区画と一緒に削除するため）。鍵（`at` の最初）がまだ無い時だけ、解析で無いことを確かめてから、`TOML.stringify` で作った区画を最後の行の後（末尾の空行の前）へ足す。`toml-patch` が文書に配列の表（`[[hooks]]`）を足せないためである。最後に改行の無いファイルや CRLF のファイルでも、元の部分のバイト列は変えない。
  - JSON: 2スペースの字下げで書く。
  - iori の項目を削除して空になった配列は鍵ごと削除する。空になった表も削除するが、削除するとユーザーのコメントも消える表は残す（例: VT Code の手順どおり `# Add your hooks here` だけを書いた `[hooks.lifecycle]`）。
- **iori の項目の見分け方**: コマンドが iori の hook（`~/.iori/hooks/` の部品）を呼ぶ項目を、iori の項目とする。どの定義の項目かはコマンドの引数の `id` で見分け、定義ごとに自分の項目だけを追加・削除する。`id` の無い iori の項目は、そのファイルを書くどの定義も削除する。
- **他の CLI の hook からの知らせ**: iori の hook のコマンドには、その定義の `id` を最後の引数として入れ、hook は知らせに `iori_cli`（その `id`）を付ける。出来事の名前と返答が無い時は、その引数に `-` を書く（Windows PowerShell は外部のコマンドへ渡す空の引数を落とし、後の引数が前へずれるため）。Terminal は、`iori_cli` が自分の CLI の `id` と違う知らせを捨てる。`iori_cli` の無い知らせ（`id` を持たないコマンドや部品から来るもの）は、その Terminal の CLI の知らせとして受ける。Grok のように他の CLI の設定（Claude Code の `~/.claude/settings.json`）も読む CLI で、他の CLI 用の iori の hook が呼ばれても、二重に数えない。正式対応の CLI の hook と部品（Pi・OpenCode）も同じく `id` を付ける。
- **出来事の名前**: `events`・`list` の形では、iori の hook のコマンドに出来事の名前も入れ、知らせの `hook_event_name` をその名前にする。`rules` の `event` は設定ファイルに書く名前で書く（VT Code の `session_start` など。payload の名前が違っても合う）。`claude-settings` では CLI の payload の `hook_event_name` を使う。
- **`rules`**: 上から順に見て、最初に合った規則で iori の状態（応答中・承認待ち・質問待ち・完了・失敗・終了）を決める。iori の hook は、`rules` に書いた出来事に足す。
  - `when` は payload の項目の値の一致で、`{ "not": … }` で否定を書ける。
  - `ignore` は、その出来事を捨てる。
  - `toolFinished` は、`toolId` の道具の実行の終わりを表示する。
  - 対応の無い出来事は捨てる。捨てた知らせからは、再開に使う会話 ID も取らない（サブエージェントの知らせなど）。
- **項目の名前**: 会話 ID・会話ファイル・応答の本文・ツール名・道具の ID・失敗の理由が、payload のどの項目に入るかを書く（`session_id` か `sessionId` か、など）。会話 ID（`sessionId`）・会話ファイル（`transcript`）・道具の ID（`toolId`）は `hooks` に、応答の本文（`response`）・ツール名（`tool`。応答中と承認待ちに使う）・失敗の理由（`failure`。先に値のある項目を使う）は規則に書く。
- 承認待ちを知らせる出来事が無い CLI では、承認待ちを推測しない。インジケーターは応答中と完了だけになる（[技術設計](../architecture.md#cli)の「承認待ちと状態」と同じ）。
- 直前の状態に依る判断（承認待ちの間の通知を無視する、など）や、道具の名前で質問待ちにする判断（Claude Code の `AskUserQuestion`）は、`rules` では書かない。正式対応のコードに残す。

## プラグインだけを持つ CLI

外部コマンドを呼ぶ hooks が無く、CLI の中で動くプラグインだけを持つ CLI（Amp・omp など）には、橋渡しの部品を置く。MiMo・OpenClaw のように外部コマンドを呼ぶ hooks も持つ CLI は、hooks の形（`events`・`list`）で書く。

- **部品の役割**: 定義ファイルと一緒に配る、その CLI のプラグインの書式で書いた小さなファイル。CLI の出来事を受け、iori へ下の「共通の形」で知らせる。
- **置き方**: 定義ファイルの `hooks`（`"format": "plugin-file"`）の `install` に、部品のファイル（`copy`、定義のフォルダーの中のファイル）と、読ませ方を `to` か `args` のどちらか一つで書く。
  - `to`（CLI のフォルダーへ置く。例: `"install": { "copy": "iori-bridge.js", "to": "~/.amp/plugins/" }`）: Host が置き場所のフォルダーへコピーする（`to` は下の「パス」の書き方が使える）。今の Pi（`~/.pi/agent/extensions/`）と OpenCode（`~/.config/opencode/plugins/`）の部品と同じ置き方である。置いた部品は下の「書き込んだ物の片付け」の記録に入れ、iori 専用のファイル（`own: true`）と同じく、iori が置いたのではない同じ名前のファイルは上書きしない。CLI の通常の起動は部品をコピーし終えるのを待たないので、その Host で初めて開く CLI の最初の会話には状態のインジケーターが出ない。
  - `args`（起動の引数で読ませる。例: `"install": { "copy": "iori-bridge.js", "args": ["--hook", "{plugin}"] }`）: Host が部品を iori のフォルダー（`~/.iori/hooks/<id>/`）へコピーし、`{plugin}` にその場所を埋めた引数を、新しい起動・再開・チームの子の起動のすべてに付ける。CLI の設定のフォルダーには何も書かないので、CLI が設定の場所を切り替える仕組み（omp のプロファイルなど）を使っても部品が読まれる。部品はコピーし終えてから起動するので、初めての起動から状態のインジケーターが出る。Host を更新しても場所が変わらないので、保存した再開のコマンドが古い場所を指さない。`args` に `{plugin}` が無い定義は、形の誤りとして読み込まない。CLI がその引数を受け付ける時はこちらを使う（omp は `--hook` を何度でも受け付ける）。
  - 確認の「CLIのプラグイン」には、`to` の時はコピーする先を、`args` の時は iori のフォルダーの置き場所を出す。
- **送るもの（`sends`）**: 部品が共通の形で送る、応答の状態以外の機能を書く（例: `"sends": ["attention", "tokens"]`）。`attention` は承認待ち・質問待ち、`tokens` はその会話の累計である。応答の状態は plugin-file の部品が常に送るので書かない。`sends` に書いた機能は「対応状況」で「利用可能」、書いていない機能は「未定義」、`"unavailable": true` の機能は「利用不可」と出す。`attention`・`tokens` 以外の値と、配列でない値は、定義の形の誤りとしてその定義を読み込まない。
- **iori の外で起動した時**: 部品は、iori が PTY に渡す環境変数 `IORI_CLI_HOOK_URL` がある時だけ知らせる。iori の外で直接起動した CLI では何もしない（今の hooks と同じ）。

## iori に知らせる共通の形

橋渡しの部品と、`rules` を通した hooks の出来事は、iori の中で同じ形になる。部品は、この JSON を `IORI_CLI_HOOK_URL` へ HTTP の POST で送る（今の Pi・OpenCode の部品と同じ届け方）。受け口は hooks の知らせと同じ URL で、`"iori": 1` を持つ本文を共通の形として受ける。Pi・OpenCode の今の部品は、道具の中身を含む生の出来事を送るので、今の形のまま残す。

```json
{
  "iori": 1,
  "iori_cli": "example",
  "state": "done",
  "sessionId": "…",
  "transcript": "…",
  "response": "…",
  "attention": { "kind": "approval", "tool": "…" },
  "outcome": "failure",
  "failure": "…",
  "tokens": {
    "input": 0,
    "output": 0,
    "cacheRead": 0,
    "cacheWrite": 0,
    "reasoning": 0
  },
  "model": "…"
}
```

- `iori_cli` は、その部品を配る定義の `id`。Terminal は、自分の CLI の `id` と違う知らせを捨てる（上の「他の CLI の hook からの知らせ」と同じ）。`iori_cli` の無い知らせは、その Terminal の CLI の知らせとして受ける。

- `state` の値と意味は、今の CLI の状態（`active`・`waiting`・`done`・`stopped`・`idle`）と同じにする。
- `tokens` は、その会話の累計。部品が CLI からトークン量を受け取れる時だけ付ける（omp は受け取れ、Amp は受け取れない）。届かなかった知らせがあっても、次の知らせの累計で正しい値に戻る。定義に `tokens` のスクリプトがある CLI では、スクリプトの値を使う。
- 知らない項目は読み捨てる。項目を足すことはあっても、既存の項目の意味は変えない。外の人が作る部品が使う約束なので、ここは互換を保つ。

## トークン量と利用枠のスクリプト

### 動かし方

- **書き方**: スクリプトは JavaScript（`.mjs`）で書く。Node.js の標準機能だけを使うよう案内するが、強制はしない。
- **動かす場所**: Host が同梱する Node.js で、Host とは別のプロセスとして動かす。Windows と Linux で同じファイルが動き、jq などの追加のコマンドを要しない。
- **入出力**: 入力は stdin の JSON、出力は stdout の JSON とする。読めなかった時は何も返さず、iori は値を出さない（推測で補わない）。
  - トークン量の入力は `{ "sessionId": "…", "transcript": "…", "cwd": "…" }`（無い値は省く）。出力は `{ "input": 0, "output": 0, "cacheRead": 0, "cacheWrite": 0, "reasoning": 0 }`（`input`・`output` は必須、ほかは CLI が記録している時だけ）。
  - 利用枠の入力は `{}`。出力は `{ "windows": [{ "remaining": 0, "minutes": 0, "resetsAt": 0, "name": "…", "modelPatterns": ["…"] }] }`。項目は今の `CliUsage` と同じで、`remaining` は残り（0〜100）、`minutes` は利用枠の長さ（分）、`resetsAt` は回復時刻（ミリ秒、無ければ省略）、`name` と `modelPatterns` は対象を分ける時の表示用（省略できる）。読み込めた利用枠が無い時は、iori は利用枠を出さない。
- **定義での書き方**: `"tokens": { "script": "tokens.mjs" }` か `"tokens": { "command": { "args": ["…"] } }`（利用枠も同じ）。`command` はスクリプトの代わりで、入出力の約束はスクリプトと同じである。`args` は 1 語ずつ引用して実行し、シェル の展開は動かさない。依存するものは、その定義を書いた人の責任とする。`"unavailable": true` を書くと、その機能が無いことを示す。
- **ファイルの場所**: スクリプトと部品の参照元は、その定義のフォルダーの中だけにする。`..` や絶対パスで外を指す定義は読み込まない。
- **環境変数**: スクリプトとコマンドは、本人のログインシェルの環境で起動する。Windows ではシステムとユーザーのレジストリの環境変数から組み立てる。Host の環境変数は引き継がず、iori の秘密値（デバイスの鍵・Forge の トークン・チームの秘密値）を渡さない。
- **重ならない**: 同じ会話・同じ CLI では、前の呼び出しが終わるまで次を始めない。固定の時間切れで失敗にはしない。

### トークン量（`tokens`）

- 入力は、会話 ID・会話ファイルの場所・作業ディレクトリ。会話ファイルの場所を hooks で受け取れない CLI（Kimi Code など）では、スクリプトが会話 ID から探す。CLI 自身がトークン量を返すコマンドを持つなら（Grok Build の `grok usage <会話ID>`）、スクリプトがそれを呼んでよい。
- 出力は、その会話の累計（`input`・`output`・`cacheRead`・`cacheWrite`・`reasoning`）。`input`・`output` は必須で、ほかは CLI が記録している時だけ返す。無い値を 0 で埋めない。
- 多くの CLI は、モデルが返した正確な量を会話ファイルに記録している。スクリプトは、それを拾って足すだけである。文字数から推定しない。
- 呼ぶ契機は、今の正式対応の CLI のトークン量と同じにする（チームの子の委譲の節目と、Board の集計）。

### 利用枠（`usage`）

- `script` を書く。スクリプトは CLI の利用枠のコマンドを自分で呼び、利用枠の一覧（残り・回復時刻・名前・対象のモデル）を返す。CLI の出力は文字や表が多く（Kiro CLI の `/usage` の表など）、項目の場所を値で書く形では足りないためである。
- スクリプトが呼ぶコマンドは、ログインを勝手に始めず、モデルを呼ばないものだけにする（[技術設計](../architecture.md#利用枠の残量)と同じ）。
- 再読み込みの契機は、今の利用枠の監視と同じにする（応答の終了、回復時刻、画面を開いた時）。

## 書き込んだ物の片付け

- **記録**: Host は、定義に従って CLI の設定へ足した hooks の項目と、置いた部品を、その Host の保存先（ユーザーの定義の `cli-definitions/` と同じ所）の `cli-definition-hooks.json` に記録する。片付けるのは、その Host の記録にある分だけである。
- **削除する時**: 次の時は、記録した分だけを削除する。
  - 定義を削除した時
  - 「同梱の定義に戻す」や編集で置き場所が変わった時
  - Host を撤去した時
- **参照の片付け（`link`）**: 記録した鍵のうち値が書き込んだ値と同じものだけを削除し、iori が作ったと記録したファイルが `link.base` だけになった時は、鍵の順を問わずファイルごと削除する。
- **同じ設定ファイル**: 同じファイルへ書く他の定義・正式対応の CLI の項目は削除しない。iori の項目をコマンドの `id` で見分け、定義ごとに自分の項目だけを追加・削除する。
- **上書きしない**: 置き場所に iori が置いたのではない同じ名前のファイルがある時は、上書きせず、その定義の部品を置かない。iori 専用のファイル（`own: true`）では、その定義の項目を除いた残りが `base` と同じか空のファイルだけを iori が置いたファイルとする（`base` の表・配列は空になっても残して比べ、鍵の順は問わない）。それ以外のファイルは、取り付けでは書かず、片付けではファイルを削除せずに、同じ設定ファイルと同じくその定義の項目だけを削除する。

## 正式対応との関係

- 正式対応の6つ（Claude Code・Codex・Pi・OpenCode・Cursor CLI・Antigravity CLI）も、定義ファイルで表せる部分（名前・コマンド・モデルの引数・最初の指示・指示のファイル・再開・`managedArguments`）は定義ファイルで書く。hooks の対応はコードに残す。CLI の名前で分かれる処理が定義ファイルと各 CLI のフォルダーに集まり、共通の処理との境界が見えるようになる。
- 次の処理は、正式対応のコードに残す。
  - 利用枠: Codex の app-server、Claude Code の `/usage` の文
  - トークン量: Claude Code・Codex・Pi の会話ファイルの読み取り
  - 失敗の理由: Codex の会話ファイルの監視
  - 起動: バージョンや OS に依る引数（Codex の共有 server を使わない起動、Windows だけのフォルダーの許可、Codex の read-only の permission profile）、Codex の `-c` の値の引用、Claude Code の `--allowedTools` の組み立て、チームの環境変数、通信フォルダー
  - hooks: 書き込み先と出来事の対応の全て（道具の中身の表示、道具の名前による質問待ち、出来事ごとの返事、Claude Code の Esc で待ちを解く処理、直前の状態に依る判断、Codex の hook の信頼の記録、バージョンによる hooks の可否を含む）
  - モデル・Effort・許可を構造で返す候補の取得
- 同梱の定義にも、定義で表せない処理だけをコードで持つ物がある。Muse Code のモデル一覧は CLI のコマンドが無いので、MSP（`muse serve`、stdio の JSON-RPC）で `initialize` → `initialized` の通知 → `model/list` を送って取る（`apps/host/src/cli/muse-code/models.ts`）。
- 正式対応の利用枠・トークン量は、本物の CLI の出力を記録した試験で正しさを保証する。定義ファイルのスクリプトから得た値は保証しない。
- Records と画面では、正式対応の値と定義ファイルの値を区別しない。正式対応以外の CLI の値が参考値であることは、ユーザー向けの文書（README）に書く。

## 同梱の定義の個別の事情

- **Muse Code**（Meta、`muse`。#328）: user hooks・project hooks・plugin の hooks には親の環境変数が渡らない（`HOME`・`PATH` など決まった変数と `MUSE_SESSION_ID` だけ）。環境変数を渡せる managed hooks を `hooks.link` で使う。`MUSE_SESSION_ID` と `MUSE_THREAD_ID` が両方あり異なる背景の subagent の hook は、主の会話の状態と再開 ID に入れない。`~/.config/muse/settings.json` は `"schema_version": 1` が必須で、無いと Muse の全コマンドが起動しない。利用枠は `muse serve` の MSP（`usage/read`・`usage/changed`・`usage/refresh`。`usage/refresh` は `initialize` で `experimentalApi` を宣言した時だけ使える。サーバーに値が無い間（今の5hの利用枠でまだ使っていない時は `server_sent_no_usage`）は `usage/read`・`usage/refresh` の応答に `usage` が無く、iori は refresh の後に `usage/read` で再取得し、値が無い間は[利用枠の表示](usage-display.md)の例外どおりに出す。値が無いのは、Meta のサーバーが鍵の発行の応答から利用枠を省くためで、未使用の間に正しい値を返す公開の API は無い（https://github.com/meta-models/muse-code-sdk/issues/9 、https://github.com/steipete/CodexBar/issues/4002 ）。dev.meta.ai の画面が使う内部の API はブラウザーの Cookie が要り、使わない）で読み、使えないバージョンでは `muse usage --json`（モデルを呼ばない。利用枠の長さは出力に無く、公式の説明から5hと7d）、トークン量は会話の記録（`~/.local/share/muse/sessions/…/session.jsonl`）の provider の量をバックグラウンドの処理も含めて足す（TUI の `/usage` の合計と同じ）。シェルの道具は OS のサンドボックスで動き、作業ディレクトリの外へ書けず、作業ディレクトリの中の `.git` も読み取り専用なので、サンドボックスありのチームの子は `iori report` と commit ができない見込み（未確認）。サブスクは学習へのデータ利用（Contributor mode）が初期値で有効。

## 今後

- 同梱の定義を本物の CLI で確かめ（まず omp）、出た不足だけ定義の書き方（`rules` の項目など）を広げる。
- 正式対応の6つの hooks の対応はコードに残し、定義ファイルへは移さない。規則で書けない判断（道具の中身、直前の状態、道具の名前による質問待ち、出来事ごとの返事、Esc）が大半で、移してもユーザーに得が無いためである。

## 参照
