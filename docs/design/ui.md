# UIの定義

部品を選ぶ時に読む。配色、書体、文字の段、状態のインジケーター、動き、画面の言葉は[画面の見た目と言葉](visual-style.md)、配置と操作は[画面の構成と移動](workspace-layout.md)が持つ。

部品はshadcn/uiとAgent Elements、分割はdockviewを使う。shadcnプリセット `bLsFFpw1Y` とBlocksを土台にし、見た目は共通の定義へ揃える。Planの縦の一覧はAgent ElementsのTodo Toolを土台にする。

右クリック（スマホは長押し）では、ioriのメニューがある行・画面はそのメニューを開き、無い所ではWebViewの標準のメニュー（再読み込み・印刷など）を出さない。入力欄と選択中の文字ではコピー・貼り付けのメニューを残す。

一つの画面は一つの部品の系統で揃える。shadcn/uiとAgent Elementsに無い部品（ファイルツリー、差分表示、ボードなど）だけを他から採り、採る前に、色をテーマの変数で指定していること、動きが控えめなこと、アイコンが同じ系統（lucide）であることを確かめる。合わない所は取り込んだ後に直す。

行の下の補足・失敗の詳細は、長い語でも面の内側で折り返す。

## 画面の骨組み

画面を作る・変える時は、部品を並べる前にこの骨組みに当てはめる。骨組み・節・欄の行・保存の知らせは共通の部品で作り、画面ごとに書き直さない。

- 上端の行: 左に題名と短い説明（戻る操作がある時は題名の上の左）、右に主な操作（保存・作成・実行など）を置く。主な操作はこの行の右だけに置き、本文の途中や左に置かない（ダイアログの例外は[ダイアログ](dialogs.md)）。例外として、Issueの詳細は題名を幅いっぱいに取るため、操作を状態の行の下に左寄せで置く（[Forge](forge.md#issues)）。設定のモーダルのように主な操作が無い画面には置かない。
- 本文: 1列に節を縦に並べる。最大幅は画面の種類で揃える: 設定のモーダルは680px、本体の編集画面（AIエージェント、チーム、Automation）は960px、表や一覧で比べる画面（Records）は本体の幅いっぱい。Files・「ファイル」のタブで描画したMarkdownはペインの幅いっぱい、Issuesの詳細（本文とコメント）は960px。節の中を別の切替（タブ・節へ移るリンク）で分けない。
- 節: 見出し（と短い説明）の下に、中身を角丸の薄い面で囲んでまとめる。面の中の行は細い線で区切り、最後の行の下には線を引かない。見出しは自分の面のすぐ上に置き、上の節からは離す。
- まとまりを近さで表示する: 同じまとまりの中の間隔は、まとまりどうしの間隔より必ず狭くする（行の中8px、見出しと面8px、行どうしは線で区切り、節どうし32px）。間隔は4pxを単位にし、隣り合うボタン・選択・入力の枠を重ねない。その操作が属するもの（保存なら自分の節の欄、「追加」なら追加先の一覧）のすぐ下・横に置く。
- 欄の形: スイッチ、選択、短い数・値は1行に置き、左に名前と説明、右に操作を置く。狭い幅で右の操作が入らない時は、名前を縮めず、操作を名前・説明のすぐ下の行へ回して右に寄せ、行の高さを中身より伸ばさない。狭い幅では、説明のある行は操作を下の行へ回す。文字の入力（名前、URL、コマンド、指示など）は名前の下に置き、複数行の欄は面の幅いっぱいに取る。
- スマホのダイアログの操作ボタンは高さを44px以上にする。
- 指で操作する端末（`pointer: coarse`）では、長押しで開くメニューの項目の高さを44px以上にする。
- 指・ポインターで開いたメニュー・ドロワー・選択の一覧は、容器にも先頭の項目にも焦点の輪を出さない。
- 押せるものは押せる見た目にする: 文字だけ・ホバーでだけ背景が出る形は、アイコンだけのボタン、一覧の行、外部のページを開くリンク（「変更内容」など）に限る。「追加」「確認」「再試行」などは枠のあるボタンにする。
- アイコンだけのボタンが並ぶ所（スマホのキーの帯など）は、既定で名前を出し、並ぶボタンの見た目をそろえる。切り替えのボタンの名前は今の状態を表示する。幅が貴重な所は、設定で名前を非表示にしてアイコンだけにできるようにする。
- 並び順: 一覧・表・行の中の項目は、ユーザーから法則の分かる順に並べる。定義の順（設定やチームで並べた順、CLIの一覧の順）、名前の順、作成の順、新しい順、状態ごとのまとまり（動いているものが先など）のどれかにし、データが届く順や絞り込みで順を変えない。同じ順の項目どうし（同じ状態・同じ時刻）も、作成の順などで決まった順にする。同じものは画面をまたいでも同じ順に並べる。ユーザーが並べ替えた時はその順に従う。
- 行の右側のアイコンと操作: 一覧の行の右側に並ぶ札・アイコン・ボタン（OS名と接続のインジケーター、歯車と＋など）は一つの組として右端へ寄せ、行の幅が変わっても組の中の間隔を変えない。開閉できる行（リポジトリ・フォルダー・worktree）の開閉のアイコン（⌄・›）は名前の左でなく行の右端に置き、＋などの操作はその左に並べる（見出し・アコーディオンの型）。開閉のアイコンと＋の位置は、この3種類の行で同じ横の位置に揃える。境界のドラッグで幅を変える所は、ホバー中とドラッグ中だけ既存の罫線と同じトークンの線を2pxにして表示する。
- 一覧の末尾の畳み（非表示にした項目 など）は常時の塗りを付けず、面の中では前後の行と同じ線で区切る。
- 行の「…」メニューは、危険な操作を区切りの下の最後に置き、項目のアイコンは、1つのメニューの中で全部に付けるか全部に付けないかのどちらかにする（右クリックのメニューも同じ）。
- 空と長い名前: 一覧が0件の時は列の見出しだけを残さず、空であることと次の操作を短く表示する。長い名前を戻る操作・上端の行・選択部品に出す時は1行で末尾を省略し、全文はツールチップで読める。worktreeの名前は中ほどを省略する。例外として、Issueの題名は読むための中身なので、上端の行でも折り返して全文を表示する。
- dockのタブは、キーボードで焦点を移した時にタブ全体の内側を輪で囲む。
- タブの選択のインジケーターは、dockのタブもペインの中のタブ（Filesのファイルのタブ、Gitの変更・履歴など）も、タブの下端に、アクセントの色の2pxの線で置く。Board のスマホの Plan・Agents のような、面の中で選んだものを白い箱で表示する切り替えの部品は、タブではないのでこの決まりの対象にしない。
- メニュー・選択の一覧の幅: 一覧の幅は並ぶ項目の長さで決め、押したボタンの幅に合わせない。画面の幅を超える時は画面の端から10px内側で止め、入りきらない項目を上の決まりで省略する。高さが画面を超える時は一覧の中でスクロールする。共通の部品（`DropdownMenuContent`）の既定にしてあり、画面ごとに幅を決め直さない。
- 取得中の見た目: 画面を開いた後に届く値（モデルの一覧、残量、Gitの状態など）を待つ間、行の下に「取得中」の段や再試行を足さず、届く値の場所を先に空けて、届く前と後で行の高さと位置を変えない。取得に失敗した時だけ、理由と再試行を出して行を伸ばしてよい。
- 読めなかった時の見た目: 見せる内容が無い時（初めて読めなかった）は、内容の場所の中央に、起きたこと・理由・回復の操作を空の時と同じ部品で表示する。最後に読み込めた内容を保っている時（再読み込みの失敗）は、上端の行の下に1行で表示する。どちらも赤は見出しかアイコンだけにし、理由は前景色、回復の操作は通常の枠のボタンにする。2つの内容を並べて比べる場所（Gitの画像の差分の変更前・変更後など）で片側だけ読み込めない時は、中央ではなく、その側のラベルのすぐ下に左寄せで1行で表示し、もう片側の表示を崩さない。読み込めたが描けない内容（表示できない画像など）は失敗ではないので、赤いアイコンを付けず補助色の文で表示し、再試行を置かない。
- 時間のかかる操作の流れ: 押してから結果が出るまでに段階がある操作（Hostの導入・更新・再起動・アンインストールなど）は、作る前に、使う人の操作の手順ごとに、画面に何が見えているべきか（押せる操作、状態、入力欄、結果）を書いて決める。押せない操作は押せない理由と、使う人ができることを表示する。iori が自動で行う待ち（再接続など）は「接続中」のように状態だけを表示し、操作を求めない。入力を求めた欄は、送信したら閉じて状態に替え、空の欄を残さない。終わったら結果を知らせる（設定などのモーダルで行った操作は、モーダルを閉じて右下の知らせに出す。右下の知らせは1〜2行の文と右上の×で、4秒で消え、ポインターを載せている間は止まる）。対処の要る注意がある完了は知らせに入れず、モーダルを閉じずに結果の画面で、1行目に済んだこと、その下に注意のアイコンと注意を表示し、「閉じる」で閉じる。進行中に閉じた後で注意・失敗で終わった時は、右下の知らせを自動で閉じず、「詳細」で結果の画面を開き直す。注意の知らせには×を置かず（閉じると結果へ戻れないため）、失敗の知らせには×を置く。「詳細」を押したら知らせを閉じる。使う人が選んでいた対象を、結果を知らせずに別のものへ替えない。
- 背景で進める操作: 確認の後も他の作業を続けられる操作（worktreeの削除）は、押したら確認を閉じ、対象の行の先頭のアイコンをスピナーに替えて名前を薄くし、押せず、メニューも出さない。行のツールチップと読み上げ名は「〈名前〉を削除中」のように全文を持たせる。完了は知らせない。失敗は行を戻し、右下の知らせを閉じるまで残す（題に対象の名前、本文は理由と対処の2文まで、「再試行…」と×。「…」は確認画面を開くことを示す記号）。確認画面は入力を奪うので自動で開かない。見ていた対象を操作した時は、押した時に別の行へ移す（「結果を知らせずに別のものへ替えない」の例外）。閉じるまで残る知らせは、狭い幅では下端の帯（接続の帯・キーの帯）を覆わないよう、その上端から8px上に置き、高さが画面を超えたら×とボタンを残して本文をスクロールする。
- ダイアログの高さ: 開いてから閉じるまで、状態が替わっても、「詳細」などの展開・折り畳みでも高さを変えない（インストーラーのウィザードと同じ）。高さは流れの中で一番長い状態に合わせて開いた時に決め、長くなりうる内容（ログ・一覧・本文）は決めた高さの欄の中でスクロールさせる。ログの欄は行数を固定し、新しい行が来たら最新の行へスクロールする。ユーザーが遡って読んでいる間は追わず、末尾へ戻したら追い直す。
- 注意・失敗の文のまとまり: アイコンの右に本文を置き、添える行（原文・アドレス・コマンドやパスの枠・切替）は本文の左端に揃える。2行を超える原文（sshの出力など）は畳み、開けば読めるようにする。スクロールする一覧・欄は下端に続きがある影を出し、横にスクロールする枠は右端をぼかす。
- 文言: 進行中の状態は「確認中」「接続中」のように「〜中」で書き、「…」を付けない。使う人に操作を求める時は「〜してください」でやることを先に書き、結果を後に書く。「〜すると〜できます」「〜してから〜できます」のように、できることを説明する形にしない。iori の中の仕組み（なぜ・どうやって iori がそうするか）と中の作りの言葉（依頼・受け付け・再取得するなど）を書かず、使う人に見える結果と、何を入れるかだけを書く。結果は「〜しました」、続いている時は「〜を開始しました」と書く。 どの語を使うかは[画面の文の語と言い回し](wording.md)に従う。
- 選択の欄と開いた一覧の長い名前: 状態のインジケーター（接続の点など）は名前の前に置き、名前は欄の幅いっぱいまで使って、入りきらない分だけ末尾を「…」で省略する。開いた一覧の幅は選択の欄の幅（スマホでは画面の幅の中）を超えて伸ばさず、項目も末尾を省略して全文はtitleで読めるようにする。2行に折り返さない。
- 押した操作の完了を待つ見た目: 削除・保存・作成・開始など、押してからHostの応答を待つボタンは、待つ間、押したボタンの文字の場所を残したまま中央に回るインジケーターを出し、ボタンの幅と位置を変えず、同じ操作を二重に送れないようにする。読み上げの名前は元の文字のままにし、ボタンの共通の部品（`Button` の `pending`）で作る。段の一覧で進み具合を表示する長い流れ（導入・アンインストールなど）では、押したボタンの中で回さず、文字のまま押せない表示にし、進み具合は段の一覧だけで表示する。
- 選択中のインジケーター: 一覧・ツリーで選んでいる行、選んでいる曜日などは、アクセントの色（薄い背景と、アイコン・下線などの表示）で表示し、非選択と一目で区別できる差を付ける。一覧と詳細を別の画面で行き来する時（スマホの設定・AIエージェント/チーム、狭い幅のFiles・Git・Issues・CI）は、一覧の行に選択中のインジケーターを出さない。ホバーの背景はマウスなどのポインターがある時だけ出し、指で押した行に残さない。一覧に戻った時に、さっき開いた項目が選ばれたままに見えないようにする（iOS・Androidの設定アプリと同じ）。
- OSが描く部品（時刻・日付の選択など）は、画面のテーマ（ライト・ダーク）に合わせて描かせる。スクロールバーはどの面でもサイドバーと同じ見た目（テーマの灰色）にそろえる。
- 画面のアイコン: 画面の入口のアイコンは下の表に従い、同じアイコンを別の画面に使わない。画面を足す時は表に足す。

| 画面           | アイコン（lucide） |
| -------------- | ------------------ |
| AIエージェント | `Bot`              |
| チーム         | `Users`            |
| Automations    | `CalendarClock`    |
| Records        | `History`          |
| CI             | `Workflow`         |
| Issues         | `CircleDot`        |

## 保存の仕方

保存の仕方は節（まとめて編集する画面では画面）ごとに一つに決め、同じ節の中で混ぜない。

- スイッチと選択だけの節: 操作したらすぐ保存する。成功の知らせは出さず、操作した部品の状態で表示する。失敗した時だけ、その行に理由を出して元の状態へ戻す。
- 文字の欄がある節: 節の末尾の右に「保存」を置き、欄の中のEnterでも保存する（複数行の欄はCtrl+Enter）。欄から離れただけでは保存しない。保存ボタンは変更が無くても押せる。結果（「保存しました」・理由つきの「保存できませんでした」）は保存ボタンの左の決まった場所に出し、出る時も消える時も他の部品の位置を変えない。失敗しても入力を残す。保存していない変更があるまま閉じる・離れる時は[破棄の確認](dialogs.md)を出す。1行の文字の欄は画面ごとに最大幅を付けず、節の幅いっぱいにする。欄の説明は共通の欄の部品の説明の位置（名前の下、入力の上）に置く。失敗の文は文字用のトークン（`--status-failed-text`）で描く。
- まとめて編集する画面（チーム、Automationの1件）: 上端の行の右に「保存」を1つ置く。保存すると新しいバージョン・新しい定義を作るので、未保存の変更が無い間は押せない（節の保存とは違う）。結果は上端の行の題名の下の行に出す。有効・無効の切替のようにすぐ反映したい操作は、編集の外（一覧の行か上端の行）に置き、すぐ保存する。
- 見るだけの画面（Records）には保存を置かない。
