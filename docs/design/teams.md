# チーム

チームは、親Agentが子Agentへ仕事を分ける回し方を、あらかじめ定義したものである。一度作ったチームは複数のプロジェクトで使い回し、複製して少し直すことで、契約の残量や新しく試したいモデルに合わせて組み替える。ioriは「どのモデルがどの仕事に向くか」の答えを出さない。日々の実務でチームを回すと記録が溜まり、後から見返して改善できるようにする。

この文書は、チームが持つ情報、子の割り当て、同時実行の上限、親の判定と記録を作る・変える時に読む。編集画面は[チームの編集画面](team-editor.md)、委譲のコマンド・子の表示・停止と再開の経路は[Linked Agent](linked-agents.md)が扱う。

## チームが持つもの

チームはHostごとに保存し、Clientを閉じても動き続ける。別のHostでは「別のHostへコピー」で同じ内容を作る。iori はいくつかのテンプレートを用意し、ユーザーはテンプレートや既存のチームから複製して独立に編集する。

| 項目       | 内容                                                                                |
| ---------- | ----------------------------------------------------------------------------------- |
| 名前・説明 | 一覧で選ぶ時に読む                                                                  |
| バージョン | 保存するたびに上がる番号（バージョン3など）。記録は、どのバージョンで動いたかを指す |
| 親         | CLI・モデル・Effort・許可の1組と、親への指示（チームの回し方の文章）                |
| 役割       | ユーザーが追加・改名・削除する。種類の区分は持たない                                |

| 役割の項目                 | 内容                                                                                                                                |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 名前・使う場面             | 親が読み、どの役割へ渡すかを決める                                                                                                  |
| 子への指示                 | 役割ごとの指示                                                                                                                      |
| 候補                       | 難易度の高・中・低ごとに優先順の一覧。各候補はCLI・モデル・Effort・許可と、残量の下限を持つ。難易度を使わない時は中の一覧だけを使う |
| 同時実行の上限             | そのチームを付けた会話の中で、この役割の子が同時に動ける数                                                                          |
| 依頼と報告の書式           | 子への依頼の項目と、子の報告の項目                                                                                                  |
| 子のセッションを再利用する | 「する」なら親は報告した子へ続きや直しを頼める。「しない」なら毎回新しい子が報告を引用して引き継ぐ                                  |

同梱のテンプレートは Development・Research・Writing・Minimal の4つ。親とすべての役割のCLI・モデルの候補は空で、ユーザーがチームを作った後に選ぶ。親のCLIが未設定でも保存できるが、会話は始められない。役割の候補が空の委譲は待機し、使える候補が無いことを一度通知する。

許可はCLIが公開する名前のまま選び、既定は「指定なし」（CLI自身の設定のまま）にする。ioriはCLIの動きを上書きして止めない。CLIが自分の機能として承認を求めた時は、ioriが検知してAttentionと通知でユーザーへ届け、ユーザーが答える。親は子の承認に答えない。承認で止めたくない時は、ユーザーがチームの候補でそのCLIの全許可のモードを選ぶ。

OpenCodeでは「Auto-approve permissions」を選ぶと、親・子を `--auto` で起動する。指定しない時はCLI自身の設定に従う。ioriのコマンドが書くセッションの通信フォルダーと、依頼書などの配送用のコピーのフォルダー（LinuxはHostの保存先の下で、別セッションのsandboxから書き換えられない。Windowsは通信フォルダーと同じ）は、チームのCLIへ起動ごとの公式の手段でアクセスを許可する（Claude CodeとAntigravity CLIなど定義に `--add-dir` を持つCLIは両方のフォルダーへ繰り返し付ける、OpenCodeはioriのpluginのconfig hookで `external_directory` へコピーのフォルダーを追加、Codexのread-onlyは通信フォルダーにだけ書けるpermission profile）。ユーザーの許可設定は一括指定・パターン指定とも保持する。ユーザーの設定ファイルは書き換えず、別のプロジェクトのフォルダーはこの許可に含めない。

チームに持たせないもの: 難易度、題名、依頼の本文、子をどのworktreeに置くかは、委譲のたびに親が決める。プロジェクトの規則はAGENTS.mdなどに置き、CLIが読む。子の時間の上限は置かず、止める時はユーザーまたは親が止める。

保存したバージョンは、親の次の委譲から使う。動いている子は、割り当てた時のバージョンのまま終わる。

## 子の割り当て

親は委譲のたびに難易度（高・中・低）を指定する。Hostは、その役割のその難易度の候補を優先順に見て、次のどれにも当たらない最初の候補を割り当てる。

- そのCLIがHostに無い
- 残量の下限を下回っている（残量を取得できるCLIだけ。その候補のモデルに適用される利用枠のどれかが下限を下回る候補を飛ばす。未ログインなどで残量が取れない時は、下限を理由に止めない）
- 同じタスクで、CLIのエラーで失敗した子と同じ割り当てである。候補のIDと、CLI・モデル・Effort・許可などの起動の設定がすべて同じ時だけ飛ばし、チームの編集で行の設定を変えた候補や新しい候補は割り当てる。準備のコマンドの失敗、報告の無いCLIの終了、停止、不採用は理由にしない。失敗した子が応答を再開して実行中へ戻ったら飛ばさない。ほかのタスクの割り当てには影響しない。止めた子を `send` で再開する時は、その子の候補のまま開き直す
- Host全体の同時実行の上限、または役割の同時実行の上限に空きが無い

候補が無い時は、同じ難易度の中だけを探し、別の難易度へ勝手に回さない。割り当てられない委譲は取り消さずに待たせ、条件が変わったら自動で進める。

- 上限に空きが無いだけなら、通知せずに空くまで待つ。
- 上限以外の理由（残量の下限、CLIが無い、このタスクで失敗したなど）で全候補が使えない時は、その委譲ごとに一度だけ通知し、チームの編集を案内する。残量がリセットされた時、またはチームを編集した時に、そのまま進む。

## 同時実行の上限

Host全体の上限は、[AI Agents/Teams](agents-and-teams.md#aiエージェント)の画面で、すべてのモデル・プロバイダー・個別のモデルの段ごとに設定する。既定は上限なし。プロバイダの段は、モデル名を `/` で区切った先頭部分を使う（Piの `openai/gpt-6.1-sol` なら、Pi全体・`openai`・`openai/gpt-6.1-sol`）。

例: Claude Code全体で2、Claude Code の Fable 5.1 で1。Pi全体は上限なし、Piの `openai` で4、`openai/gpt-6.1-sol` で2。

子を割り当てるのは、その候補が属する全部の段に空きがある時だけである。Hostが数えるのは、iori が起動したCLI（親、子、ユーザーが開いたCLIのタブ）だけで、ioriの外で動いているものは数えない。上限で待たせるのは子の割り当てだけで、ユーザーが開く会話やタブは止めない。通常のタブのモデルがCLIから分かるまではCLI全体の段だけで数え、分かったらプロバイダ・モデルの段にも数える。モデルは推測せず、不明であることだけを理由に割り当てを止めない。

別のCLIから同じサーバーを使う場合（PiとOpenCodeから同じllama.cppを呼ぶなど）は、別の名前として数える。ユーザーが片方のCLIだけを候補にするなどで調整する。

## 親の判定

子の報告を受け入れるか直させるかは、親が決める。レビューの役割の子の意見を、ioriは判定として扱わない。

- 親が子へ直しを送る時は、送るコマンドに「差し戻し」を付ける。質問への回答や追加の依頼とは分けて数える。
- 親が子を終える時は、「受け入れ」か「不採用」と短い理由を付ける。軽い指摘をIssueに回して進める時も「受け入れ」とする。
- 判定はコマンドの必須の引数にし、親の文章から推測しない。続きのタスクで役割を替えた時はタスクの役割も替える。古い子への判定はその子だけへ記録し、同じタスクを続ける新しい子の判定にしない。
- 差し戻しはタスクごとに数える。親は委譲の時に、どのタスクの続きかを指定でき、新しい子が直しを引き継いでも数を引き継ぐ。初回受入は、差し戻しが0回のまま受け入れたタスクである。

## ユーザーと子

ユーザーは普段は親と話す。子の画面を開いて今の作業を見られ、子へ直接入力でき、子のタブとサイドバーの子の行から子を止められる。ユーザーが子へ送った内容と止めたことは、親が次に子の状況を読む時に分かる。それを理由に親の応答を勝手に始めない。

Hostの再起動で親の会話を戻す時、親への指示のファイルが欠けていれば、その会話を始めた時のチームのバージョンから通常の起動と同じ形で作り直す。バージョンが無い（チームを削除した）・作り直せない会話だけは戻さず、その会話の「再開」は失敗を表示する。ほかの会話とHostは通常どおり起動する。

## 記録

最初のバージョンから、タスクと子ごとに次を記録する。値の無い項目は記録・表示せず、0や親の値で代用しない。

- チームとバージョン、役割、難易度、割り当てた候補（CLI・モデル・Effort・許可）。結んだ計画のタスク（[Board](board.md#親の計画)）
- 差し戻しの回数と、それぞれの時刻・担当・本文
- 子からの質問の回数
- 親の判定と理由、その時刻
- 子ごとの開始・終了の時刻と経過時間（割り当てを待つ時間は含めない）、作業時間。作業時間は、経過時間から子が人や親を待っていた時間（CLIの許可の承認待ち、親への質問の回答待ち、応答を終えて入力を待つ間）を除いたもの。CLIの起動から状態の変わり目の時刻で数え、CLIが起動していない子には付けない。作業時間を記録する前のタスクは経過時間をそのまま使う
- 変更の量（追加と削除の行数を分けて、ファイル数）
- トークン量: 子のCLIが自分で書くセッションの記録から、入力＋出力を読み込む（キャッシュと推論の量は内訳として分けて持つ）。Claude Code・Codex・Piから取り、取れないCLIでは記録しない

見返す画面は[Records](records.md)が扱う。

## 後で決めること

- 差し戻しがn回目になったら別の候補へ回す設定。
- 難易度の判定をJevなどの意思決定モデルに任せるか。任せる場合、iori が外部のAPIを呼ぶか、判定を役割の一つとしてCLIに任せるか。
- 親が `iori plan` で計画を更新しない状態が日常利用で続く時の、計画の取り方の見直し（CLIのToDoを拾う、委譲だけを行にする、など）。
