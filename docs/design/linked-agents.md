# Linked Agent

Linked Agent は、会話にチームを付け、親Agentが子Agentへ仕事を分ける機能である。この文書は、チームの会話の始め方、親と子のコマンド、子の起動・表示・停止、親への知らせを作る・変える時に読む。チームが持つ項目・子の割り当て・同時実行の上限・親の判定と記録は[チーム](teams.md)、編集画面は[チームの編集画面](team-editor.md)が正本である。

親と子はどちらもCLI自身の画面（PTY）で動き、同じHostにいる。会話の状況を一目で知るタブと親の計画のコマンド（`iori plan`）は[Board](board.md)が扱う。

## チームの会話を始める

タブの「＋」の一覧で、CLIの群の下に「Team」の群を置く。チームを選ぶと、そのチームの親の設定（CLI・モデル・Effort・許可）で親のCLIを起動し、チームの回し方と親への指示を渡す。既定のチームは群の先頭に出す。CLIを直接選んだ時はチームの無い会話になる。チーム機能がオフの時は群を出さない。

会話の途中でチームを付ける・替える操作は作らない。CLIの画面には、後から指示を確かに差し込む方法が無いからである。親への指示を保存し直した時は、新しく始めた会話から反映される。役割と候補の変更は、動いている会話でも親の次の委譲から反映される（[チーム](teams.md#チームが持つもの)）。

## 親と子のコマンド

Hostは、チームの会話の親と子のシェルに `iori` コマンドを用意する。チームでない会話にも同じコマンドを用意し、そこではForgeを読み込むコマンドだけを使える（[Forgeとの連携](forge.md#aiエージェント向けのコマンド)）。ログインシェルがPATHを置き換える環境に備え、固定の指示にはHostの実際のコマンドの場所を埋め込み、そのOSのシェルで呼ぶ書き方を渡す。まず `iori` を使い、見つからない時だけその場所で呼び直す。Claude Codeには絶対パスでの呼び方も許可する。Clientで見る手引きでは、実際の場所の代わりにHostが渡すコマンドの場所と表示する。Codexは公式の `allow_login_shell=false` を指定して起動し、Hostのシェルがprofileを読み込んだ環境を各コマンドへ引き継ぐ。チームでない会話では、ユーザーが起動時の引数で `allow_login_shell` を指定していればその指定に従う。Windowsのコマンドは `iori.exe` とし、PowerShell・cmd・Git Bashから同じ名前で呼べる。Windowsの本文は作業ディレクトリの中のファイルを `--file` で渡すか、`--body -` で渡す。どのCLIもシェルを実行できるので、CLIごとの道具の仕組みに頼らない。

| 使う人 | コマンド        | 責任                                                                                                           |
| ------ | --------------- | -------------------------------------------------------------------------------------------------------------- |
| 親     | `iori delegate` | 役割・難易度・題名・依頼の本文・作業場所を受けて委譲する。どのタスクの続きかを指定でき、差し戻しの数を引き継ぐ |
| 親     | `iori plan`     | 会話の目標と計画を登録・更新し、再度確認する（[Board](board.md#親の計画)）                                     |
| 親     | `iori tasks`    | 子とタスクの状況（起動中・実行中・待機とその理由・報告済み・質問・終了）を返す                                 |
| 親     | `iori read`     | 子の報告・質問を読む                                                                                           |
| 親     | `iori send`     | 子へ「回答」「追加の依頼」「差し戻し」のどれかを必須の引数で分けて送る                                         |
| 親     | `iori finish`   | 「受け入れ」か「不採用」と短い理由を必須の引数にして子を終える。子のworktreeを残すか削除するかも指定する       |
| 親     | `iori stop`     | 子の作業を止める                                                                                               |
| 子     | `iori report`   | 依頼の書式に沿った報告を親へ出す                                                                               |
| 子     | `iori ask`      | 作業上の質問を親へ出してすぐ戻る。回答は子のCLIの画面へ届く                                                    |

`tasks` には最新の役割名と「使う場面」も含める。親は次の委譲の前に読んで、保存後に追加・改名された役割も選べる。

コマンドの答えはCLIが読める英語の短い文で返す。委譲の返答は、割り当てが決まったら `starting`（起動開始）、すでに起動した場合は `running`（実行中）、上限の空き待ちは `waiting (capacity)`、使える候補が無い時は `waiting (candidates)` を表示する。worktreeの作成やCLIの起動完了を待たずに返す。

`--json` は `ok` と `data`（構造化した値）を返し、構造化した値が無いコマンドは `ok` と `text`（返答の文）を返す。`data` と同じ内容の `text` は重ねて出さない。委譲の `data` には子とタスクのID、起動開始か待機かの状態、待機する時はその理由を含める。本文は `--body TEXT`、`--file PATH`、`--body -`（標準入力）のいずれかで渡す。`iori --help` でも次の書式を読める。`iori --help` は書式の後に、[worktree作成後に実行するコマンド](worktrees.md#作成後に実行するコマンド)を動かす場所・シェル・`IORI_ROOT_PATH`・成否の扱いも短く表示する。Agentにこのコマンドを考えさせるユーザーのためである。

`--file` は呼び出したプロセスの作業ディレクトリ内のファイルだけを読み、外を指すsymlinkも拒む。作業ディレクトリ外の本文は、CLI自身の許可を通る読み取りコマンドから `--body -` へ渡す。

```sh
iori delegate --role NAME --difficulty high|medium|low --title TITLE --worktree new|parent|NAME [--repo PATH] --body TEXT [--continue TASK_ID] [--plan N]
iori plan show|goal|add|update|cancel
iori tasks
iori read CHILD_ID
iori send CHILD_ID --kind answer|request|revise --body TEXT
iori finish CHILD_ID --decision accept|reject --reason TEXT --worktree keep|remove [--discard]
iori stop CHILD_ID
iori report --body TEXT
iori ask --body TEXT
```

子には役割の指示・親の依頼・引用した報告を渡し、親の会話全体は渡さない。子はチームを持たず、孫へ委譲しない。トークン量は上限として強制しない。

「子のセッションを再利用する」が「する」の役割では、報告した子は待ちのまま残り、`send` の回答・追加の依頼・差し戻しはその子へ届く。「しない」の役割では、質問への回答だけはその子へ届き、追加の依頼と差し戻しはHostが報告を引用して新しい子へ委譲する（同じタスクとして数える）。

## 子の起動と作業場所

Hostは[チーム](teams.md#子の割り当て)の規則で候補を割り当て、そのCLIをモデル・Effort・許可を付けてPTYで起動し、依頼を渡す。割り当てを待つ委譲は取り消さず、条件が変わったら進める。

画面への入力で最初の依頼を渡す時は、CLIのSessionStartのhookがある時はその通知を待ち、無い時はブラケットペーストのモードが有効になった時に送る。どちらの準備も示さないCLIには、最初の出力の後で出力が落ち着いた時にも送れる。定義で `launch.initialPrompt.mode=paste` を指定したCLIは、ブラケットペーストのモードが有効になるのを待つ。準備を待つ時間で子を失敗にはしない。

作業場所は親が `delegate` で選ぶ。`new` はHostが親のリポジトリに新しいworktreeとブランチを作り、`parent` は親と同じworktree、既存のworktreeは名前で指す。`--repo` を付けると、親と別のリポジトリ（同じHostのGitリポジトリ）に子を置ける（[別のリポジトリに子を置く](worktrees.md#別のリポジトリに子を置く)）。作ったworktreeは[worktreeとフォルダー](worktrees.md)の規則で表示し、`finish` で削除する時の条件も同じ文書に従う。`finish --worktree remove` では、Gitで消した後に残ったファイルも消す。役割に場所の欄は置かない。WindowsのCodexには、チームの有無にかかわらず、そのセッションのコマンド通信フォルダーを公式の `--add-dir` で渡す。本人の設定がread-onlyの場合や、選んだpermission profileの書き込み範囲が分からない場合は渡さない。チームの候補やAutomationでCodexの `read-only` を選んだ時は、`:read-only` に通信フォルダーへの書き込みだけを足したpermission profileを使い、`iori` のコマンドを承認なしで使えるようにする。Windowsのunelevated sandboxではread-onlyを使い、通信フォルダーは追加しない。許可を「指定なし」時と「＋」から始めた会話は本人のCodex設定を使う。通信フォルダーを渡さない場合、`iori` の実行にはCLIの承認が要り、承認を求めない設定では使えない。Windowsのelevated sandboxで本人の設定がread-onlyの時は、依頼書の読み取りにも承認が要り、承認を求めない設定では依頼書を読めない。unelevatedでは依頼書を読める。Claude Codeのチームの親と子には、ioriのコマンドとチームのファイルのフォルダーだけを許す起動オプションを付ける。

## 親への知らせ

子が報告した時、質問した時、失敗した時（報告せずに終わった時を含む）、Hostは親のCLIへ「Worker（題名）が報告しました。`iori tasks` で確認してください」のような一行を送る。親が待っている時も、応答している時も、ユーザーが親の入力欄に書きかけの時も送る。応答中に届いた入力の扱い（割り込み・後回し）はCLIに任せる。書きかけの文は、その一行と一緒に送られる。CLIが承認・質問の選択を出している間は、それを抜けてから順に送る。親から子への回答・追加の依頼・差し戻しも同じ扱いとする。保留中の `send` は「未配送」と返し、`iori tasks` に未配送の回答の件数を表示する。CLIへ書き込む前に停止・終了した回答は残し、親の `send` で子を再開した時に順番に届ける。親への知らせが保留のまま失われた場合も、`iori tasks` に未配送と記録する。CLIへ書き込んだ後に処理したかどうかは推測せず、自動で再送しない。

CLIがエラーで応答を終えた子は失敗とし、CLIが出した理由をサイドバー・Boardと親への知らせへ付ける。理由を取れない場合も失敗は知らせる。失敗の子はサイドバーでも畳まず、行のメニューから停止できる。エラーだけではCLIを終了せず、ユーザーの再入力や親の`send`でCLIが応答を再開すると実行中へ戻る。

このCLIのエラーの知らせには、タスクのIDと、`delegate --continue` でそのタスクを委譲し直すと次の候補で動くこと、新しい子は前の会話を持たないので依頼を単独で読める形で書くことを添える。委譲し直すと、Hostは前の子を親の操作として止めてから、[チーム](teams.md#子の割り当て)の規則で候補を割り当てる。失敗した子のCLIは終了していないので、止めないと役割の上限の枠とworktreeを使い続けるからである。

`delegate --continue` は、前の子が終了・停止していない時は、停止してから引き継ぐ。

`delegate --continue` で前の担当がいる時は、報告済み・受け入れ済み・親が止めた子を含め、親が今回書いた本文の後に「前の担当について」の節を付ける。節には前の担当のCLI・モデル、引き継ぎの状態、前の依頼の全文、作業場所を書く。状態はCLIのエラー、親がfinishした時の判定と理由、その他の失敗、停止理由、報告済み、未報告をこの順で書き分ける。前の依頼の全文には、その子への依頼に続けて、親がその子へ送った回答・追加の依頼・差し戻しを送った順に入れる。作業場所は、同じworktreeなら途中の変更が残っているかもしれないので `git status` と差分を見てから続けること、別のworktreeならその場所とし、worktreeを削除した後は書かない。前の担当も同じように引き継いでいた時は、その節も続けて書く。報告がある時は、節に加えて報告を引用する。

子が親の依頼への応答を終え、報告も質問もせずに入力待ちになった時も、同じ経路で親へ一行知らせる。入力待ちはCLIのhook・出来事で判断し、承認や質問の選択待ちは含めない。同じ応答の終わりでは一度だけ知らせ、親の `send` で始まった次の応答も同じように扱う。`iori tasks` では子の状態の種類を増やさず、`waiting: "report"` と `waitingReasons: [{ reason: "no_report" }]` で未報告の入力待ちを表示する。

子がバックグラウンドで流したコマンドを残して応答を終えた時は、入力待ちとせず、作業中のままにする。CLIは処理が終わると自分で次の応答を始めるので、知らせを送らず、その次の応答の終わりで報告の有無を判断する。待っている処理は `iori tasks` の子に、CLIが渡したコマンドと説明で表示する。判断に使うのはCLIの公式のhook・出来事だけで、それを出すのは今はClaude Code（`Stop` の `background_tasks` の `status: "running"`）である。出さないCLIは応答の終わりで判断する。

ユーザーが子へ送った内容と、ユーザー・Hostの再起動による停止では親へ送らない（[チーム](teams.md#ユーザーと子)）。子の画面への入力に続いてCLIが終了した場合も、ユーザーの操作による停止として記録する。親は次に `iori tasks` を読んだ時に知る。ユーザーが子の画面へ直接入力して始めた応答や、親の依頼への応答中にユーザーが入力した後の応答の終わりも、未報告の入力待ちの知らせを送らない。中断のキー（Esc・Ctrl+Cなど）も入力に含める。

親のCLIが終了したら、まだ起動していない委譲を「親の終了」で取り消す。動いている子は続け、報告・質問は記録に残し、終了した親へ入力を送らない。親のCLIを再開すると、同じ会話の `iori tasks` と `iori read` で記録を読め、新しく委譲できる。

子のCLIが承認を求めた時は、親へ渡さず、Attentionと通知でユーザーへ届ける。CLI自身の確認も、公式のhookや出来事が出るものは同じ経路で知らせる。hookの起動前に出るフォルダー信頼の確認など、CLIが出来事を出さない確認は子の画面でユーザーが答える。画面の文字から状態を推測したり、ioriが代わりに答えたりはしない。ただし、ioriが子のために作ったworktreeは、委譲の時点でユーザーがそのリポジトリを信頼しているとみなし、CLIが起動の引数でその起動だけの信頼を渡せる時は、信頼済みとして起動する（Antigravity CLI は `--settings` の `trustedWorkspaces`。CLI自身の設定ファイルは変えない）。

子への初回依頼と親からのメッセージは通常のファイルで渡し、CLIのファイル読取ツールで開くことを知らせと子の固定の手引きに明示する。`iori read` は親が子の報告・質問を読むコマンドであり、子のファイル読取には使わない。

## 子の表示

子のタブは自動では開かない。サイドバーの親の下に子の行を置き（配置は[画面の構成](workspace-layout.md)）、役割、題名、CLIとモデル、状態、経過時間を表示する。状態は、起動中、実行中、待機（同時実行の上限で待機中／使える候補が無い）、承認待ち、報告済み、質問中、失敗、終了（受け入れ・不採用・停止）。子の行は2段にする。1段目は状態のインジケーター・太めの役割・薄い題名・右端の経過時間、2段目はCLIのアイコンとモデル・状態の文字を小さく薄く表示する。題名と長い状態は末尾を省略し、行全体の説明から全文を読める。子のAgentの状態のインジケーターと子のworktreeのブランチアイコンは、親の会話の題名の文字の始まりにそろえて字下げする。子のAgentの行の高さは2段の分だけ親の行より高くする。行を押すと親の配置の中に子のCLIのタブを開き、ユーザーはそこで画面を見て入力できる。

子はworktreeごとにまとめ、各まとまりの中は状態のまとまり（未決の報告済み・質問中・失敗、実行中など、待機）の順に並べ、同じ状態のまとまりでは委譲した順に並べる。

報告済み・質問中でも、CLIが作業中の間は状態のインジケーターと文字をRunning（実行中）にし、報告済み・質問中であることは2段目の補足に残す。CLIの作業が止まったらReported・Questionへ戻す。承認待ちの扱いは変えず、`iori tasks` は報告済み・質問中の状態を返す。

状態の補足は今の状態の理由だけを表示する。失敗後に止めた子は、サイドバー・BoardともStoppedと停止した理由を表示し、前の失敗理由は連ねない。

親が子を終えると子のCLIを終了し、タブを閉じる（Orcaと同じ）。終わった子の行は畳んで残り、押すとHostが保持した最後の画面を読める。開き直した最後の画面は、ほかの子の状態が変わっても閉じない。親の会話の行を「閉じる」で削除した時は、その子の行もサイドバーから削除する。Hostの記録は残す。

## 停止、再開、通知

ユーザーは子の行とタブから、親は `iori stop` で子を止められる。止めると子のCLIのプロセスを終える。止めた理由（ユーザーの操作・親の操作・Hostの再起動）を子の行と `iori tasks` の答えに表示する。

止めた子へ親が `send` すると、HostはCLIの再開機能でその会話を開き直して届ける。再開機能の無いCLIでは、報告と履歴を引用して新しい子へ委譲する。専用の再開ボタンは作らず、ユーザーは親へ「Workerを再開して」と頼む。

通知と接続の詳細は[接続](connection.md)に従う。

## 記録

タスクごとの記録は[チーム](teams.md#記録)に従う。親の判定と子の報告を、ユーザーの指示や権限と混同しない。
